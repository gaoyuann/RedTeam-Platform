# 云笔电性能排查与优化

本次针对“打开任务、切换页面、滚动时卡顿”检查客户端、接口、数据库访问和构建方式。以下结论来自仓库代码和本地隔离测试，尚无云笔电实机的帧耗时、CPU 或内存采样，不能把测试数据当作实机加速比例。

## 已核实的开销与改动

| 位置 | 原有行为 | 调整后 |
| --- | --- | --- |
| `backend/src/routes/pipelines.js` | 列表 `SELECT *` 返回历史分析、执行结果等大字段 | 增加 `GET /api/pipelines?view=list`，只查询列表使用的身份、目标、状态、配置和时间；原接口及详情保持兼容 |
| `frontend/src/pages/FlowPage.cpp` | 每输入一个搜索字符、切换筛选条件都重新请求任务列表 | 使用当前成功读取的列表在本地筛选，输入停顿 150ms 后更新 |
| 同上 | 定时刷新、WebSocket 和操作回调可同时请求列表或详情 | 每类请求最多一个在途请求和一个待刷新意图；任务事件在 100ms 内合并，保留任务身份和版本校验 |
| 同上 | 列表每次清空重建；运行中的任务即使数据相同也重新更新所有子页面 | 相同列表和详情跳过重建；列表变化时保留可见选中任务和滚动位置，批量填充期间暂停绘制；独立变化的扫描、执行数据仍刷新可见页 |
| `frontend/src/pages/TaskExecutionPanel.cpp` | 执行快照每次采集时间变化都会重建表格 | 比较业务内容，忽略单独变化的 `captured_at`；失败后保留并标记旧快照，恢复成功时重新渲染以清除错误 |
| `frontend/src/pages/ScanPage.cpp`、`ExecutionPage.cpp` | 已启动的扫描、执行轮询在隐藏页面也会运行 | 定时刷新仅在页面可见时执行，重新显示时补读；手动刷新仍可用，后台实际任务继续由服务端执行 |
| 根 `CMakeLists.txt` | 普通单配置构建未指定优化类型 | 未指定类型时默认 Release；显式选择 Debug、多配置生成器和现有 Debug 缓存保持原设置 |
| `frontend/src/MainWindow.cpp` | 登录后一次创建全部模块，未打开的页面也构建大量控件、读取扫描与管理数据 | 首次只创建首页与锁屏页，其余六个模块使用占位页；进入时创建一次并复用，创建任务模块时再绑定其 WebSocket |
| `frontend/src/pages/DashboardPage.cpp` | 每个实时事件都重新查询首页四组数据，首页隐藏时也会刷新 | 实时事件在 100ms 内合并；一组请求完成前只保留一次补读；隐藏时标记待刷新，重新显示后读取 |
| `frontend/src/pages/TopologyPage.cpp` | 拖动一个节点后清空并重建全部节点、连线和标签 | 拖动过程中按节点的相邻边索引更新连线与标签；释放时保存坐标并调整场景范围，保留所有图元及属性选择 |

`view=list` 不返回 `analysis_result`、`result` 或 `error_message`，也不新增统计查询。列表仍按原权限、状态条件和时间顺序返回，`config` 保持原字符串，兼容旧数据。旧客户端不传参数时仍获得原响应；新客户端连接旧后端时，旧接口会忽略查询参数，功能可继续使用，但响应体积不会减少。

工作台首页会使用原列表中的分析数据汇总候选风险，因此本次只让测试任务列表使用精简响应。现有默认列表和详情仍可能较大；历史任务非常多时，后续可增加分页与专用汇总接口，需要同时调整统计口径及调用方。

## 验证

后端使用内存数据库、模拟用户和仅绑定本机的测试接口，不迁移实际数据库、不调用扫描器：

```bash
cd backend
node --experimental-test-module-mocks --test test/pipeline-list-performance.test.js
npm test
```

精简接口用两个任务、每任务两个 512 KiB 大字段的固定数据进行比较：旧响应 2,097,974 字节，精简响应 498 字节。这个结果只说明此测试数据下省掉大字段的效果；真实任务的大小和配置不同，减少比例也不同。测试同时检查所有者隔离、管理员可见范围、状态筛选、空结果、旧配置和重复读取不改变数据。

前端使用现有 CMake 目录和隔离 HTTP 模拟服务：

```bash
cmake --build build --target RedTeam-Platform RedTeam-Platform-Batch16Checks -j2
ctest --test-dir build -R '^ui-context-' --output-on-failure
```

第二轮还使用现有首页和拓扑测试目标验证：

```bash
cmake --build build --target RedTeam-DashboardChecks -j2
ctest --test-dir build -R '^ui-dashboard$' --output-on-failure
cmake --build build/topology-ui -j2
ctest --test-dir build/topology-ui --output-on-failure
```

回归覆盖 1 / 1.25 / 1.5 倍缩放，以及：

- 搜索不增加 HTTP 请求，清空搜索恢复已有任务。
- 模拟慢响应下，40 次连续列表或详情刷新只产生一次当前读取和一次补读；40 次步骤事件合并为一次详情读取。
- 相同列表保留表格对象和选择，相同运行中详情保留分析表格，只有采集时间变化的执行快照保留执行表格。
- 失败后可以重试，成功恢复会清除旧错误，业务内容变化仍更新展示。
- 隐藏页的定时器不发送请求；原有跨任务旧响应隔离、扫描完成、执行历史和报告检查继续运行。
- 登录后的六个未打开模块保持占位状态，不读取任务、预案和管理数据；从分析页跳转可正确创建任务模块，多次进入仍使用同一实例，加密锁阻止未打开模块的创建。
- 首页 40 次连续事件只触发一组四个请求；慢响应时 40 次手动刷新合并为当前一组和后续一组；隐藏期间不发请求，返回时补读。
- 真实鼠标拖动拓扑节点期间，相关连线和标签立即移动，无关连线保持原样；释放后场景代次及所有图元不变，保存后的坐标与画面一致。

## 云笔电生效与复测

需要发布更新后的后端并重新编译客户端才能获得全部效果。本次没有进行远端部署、服务重启、容器变更或系统配置修改。

现有缓存若为 Debug，不会自动改成 Release。正式客户端构建可在项目目录明确配置后编译：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target RedTeam-Platform -j2
```

保留原有编译器和 Qt 版本。编译后通过原有入口重新打开客户端。建议在同一台云笔电、同一网络与任务数据下比较：任务列表滚动、打开一个运行中任务、连续切换扫描/分析/执行页、打开长执行记录、返回列表搜索。

复测时可在本机终端检查 `free -h`、`uptime` 和 `ps -C RedTeam-Platform -o pid,%cpu,%mem,rss`。同时分别记录第一次打开与重复打开的等待时间，以及是否仅运行扫描时变慢。现有开发环境的资源读数不能代表云笔电。

如果上述场景仍卡顿，下一步应在实机区分 GUI 主线程耗时、网络等待和远程桌面绘制耗时。下面几项仍有进一步优化空间，但尚未量化实机影响：

- 任务模块内部的多个阶段页、系统管理内部的多个子页仍在首次打开模块时一起创建，可继续按需加载，但需要维护阶段上下文与权限状态。
- 首页仍读取任务分析正文来统计候选风险；分析索引也会解析当前账号的所有任务后再分页。数据量大时可改为后端专用汇总、分页查询，需要保持旧数据解析、权限隔离和统计口径。
- 知识图谱布局在 GUI 线程执行，可在实测耗时明显时移到工作线程，并处理取消和过期结果。
- 加密锁校验同步访问设备，需结合硬件耗时决定是否异步化；本次保留原有校验策略。

第二轮只修改客户端及验证代码，无新增 API 或数据库迁移；单独部署第二轮改动只需更新客户端。
