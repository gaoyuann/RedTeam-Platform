## 问题一：任务执行失败 🔴

### 现象

对 DVWA 靶场发起漏洞攻击测试任务，任务执行失败。

### 实测诊断结论（2026-10-07 查日志确认）

查 `data/redteam.db` 中最近一次失败 run（`run_86c2ea4a-3b0`，2026-10-06 17:07，target=172.17.0.2）：

- `target_class` = `local_ip`（隐患仍在，但**非本次直接原因**——这次用的是 AI 生成的通用 playbook `gen_1791306333629_2crfvv`，步骤为 whatweb/gobuster/nikto/nuclei，不依赖 DVWA 专用变量）
- `preflight_status` = `PASSED`（旧预检结果；不能据此证明所需镜像和字典文件都存在）
- 9 步里 7 成功 2 失败，`hasNonOptionalFailure:true` → FAILED

**10 条工具证据逐条核对**：

| step | tool | success | 关键输出 |
|------|------|---------|----------|
| 0 | whatweb | ✅ | Apache 2.4.25 (Debian), Title[SYSTEM COMPROMISED] |
| 4 | gobuster | ❌ | `wordlist "/usr/share/wordlists/dirb/common.txt" does not exist` |
| 4 | gobuster | ❌ | `wordlist "/usr/share/wordlists/dirbuster/directory-list-2.3-small.txt" does not exist` |
| 4 | nikto | ✅ | SSL support not available（仅警告，HTTP 扫描正常） |
| 1 | gobuster | ❌ | 同上字典缺失 |
| 4 | ffuf | ✅ | 正常 |
| 4 | curl | ✅ | 200 OK |
| 4 | nikto | ✅ | 正常 |
| 2 | nikto | ✅ | 正常 |
| 3 | nuclei | ✅ | **发现 `[dvwa-default-login] [critical] admin/password`** |

**本次失败直接根因：运行时挂载路径下缺少所需字典文件**

后续核查发现，`toolRunner.js` 将宿主机 `data/wordlists/` 挂载到 `/usr/share/wordlists`，遮盖镜像内同路径。以下镜像检查属于首次诊断记录；镜像内是否带字典不能代替实际挂载目录的文件检查。

- gobuster 跑在 `rt-recon` 容器（`containers/recon/Dockerfile`）
- 该 Dockerfile **只 wget gobuster 二进制，没装 wordlists**
- `docker run --rm rt-recon ls /usr/share/wordlists/` → `No such file or directory`
- 代码硬编码引用 `/usr/share/wordlists/dirb/common.txt`（`genericWebTargetAdapter.js:50`）和 `dirbuster/directory-list-2.3-small.txt`，容器内均不存在
- gobuster 是非可选步骤，连续 3 次失败 → `hasNonOptionalFailure:true` → 整个 run 标记 FAILED

**注意**：nuclei 已成功发现 DVWA 默认登录 `admin/password`，靶场本身完全正常，工具链路也通，**唯一卡点就是 gobuster 字典缺失**。

### 根因分析（5 个疑点，按可能性排序，已据实测重排）

#### 疑点 1（最可能）：DVWA 上下文变量未构建

**根因链：**

1. `targetProfileResolver.js:19` 中 `DVWA_HOSTS = new Set(['localhost', '127.0.0.1', '0.0.0.0'])` —— **`172.17.0.2` 不在此集合**。
2. `172.17.0.2` 匹配私有 IP 模式 `172\.(1[6-9]|2\d|3[01])` → 被分类为 **`local_ip`**，而非 `dvwa`。
3. `executionEngine.js:222` 只查询 `SELECT target_type FROM playbooks`，**不查询 `metadata` 列里的 `dvwa_profile`**。
4. `executionEngine.js:228` 调用 `buildContextForTarget(targetProfile)` —— **不传 `dvwaProfile` 参数**。
5. `targetAdapters/index.js:38` 条件 `if (dvwaProfile && dvwaProfile.base_url)` 永远为 false（dvwaProfile 默认 `{}`）。
6. 对 `local_ip` 走 `buildWebContext()` 而非 `buildDvwaContext()`，**不提供** `sqli_url` / `dvwa_sqli_url` / `dvwa_login_url` / `dvwa_cookie` / `security_level`。
7. 使用这些变量的 playbook（如 `sqli_to_shell.json` 步骤 1-2 用 `{{sqli_url}}`、`{{dvwa_cookie}}`）渲染失败。
8. `commandTemplateRenderer.js:56` 未找到的变量保留原始占位符 → sqlmap 收到 `-u {{sqli_url}}` 作为参数。
9. sqlmap 无法解析 `{{sqli_url}}` 为有效 URL → 步骤失败 → 非可选步骤失败 → 执行标记为 FAILED。

**影响范围**：所有使用 DVWA 专用变量的 playbook，当目标为 `172.17.0.2` 或任何非 localhost 的私有 IP 时。

**附注**：`sqli_to_shell.json` 本身甚至没有 `dvwa_profile` 字段，所以即使修复了 executionEngine 的加载逻辑，此 playbook 仍会失败——需要将 `172.17.0.2` 纳入 DVWA 识别逻辑，或在 playbook 中显式设置 `dvwa_profile.base_url`。

#### 疑点 2（高可能）：审批门导致执行"看似失败"

- `pipelineEngine.js:618`：`requireApproval = pipelineConfig.require_approval !== false` —— **默认 true**。
- `FlowPage.cpp:538`：创建对话框中审批复选框默认勾选。
- 流水线在生成 playbook 后暂停于 `awaiting_approval` 状态，不自动执行。
- `FlowPage.cpp:761` 的 `onPipelineStatus` 在 `awaiting_approval` 时不自动切 Tab，用户可能看不到"选择预案并执行"按钮，误以为卡住/失败。

#### 疑点 3（高可能）：容器镜像未构建 / 容器引擎不可用

- `containerEngine.js:20-35` 检测顺序：podman → docker → fallback `host`。
- 若引擎为 `host`，`toolRunner.js:229` 直接在宿主机执行二进制 —— 宿主机若未装 nmap/nikto/sqlmap 则 spawn 失败。
- 若容器引擎可用但镜像（`rt-recon`、`rt-vuln-scan` 等）未构建，`docker run rt-recon ...` 因 "image not found" 失败 —— **不会 fallback 到 host**，直接返回失败。
- `preflightGate.js:169` 的 `tool_binaries` 检查只检测引擎是否存在，**不检测镜像是否存在**。

#### 疑点 4（中可能）：Playbook 匹配/生成失败

- `pipelineEngine.js:378-407`：AI 生成依赖 LLM API key，无 key 则生成失败；匹配 fallback 调 `matchPlaybooks(allResults, profile.target_class)`，若扫描无结果或无匹配 playbook，行 401-402 标记步骤失败，行 406 返回 `{ok: false, error: '无法生成或匹配 Playbook'}`。

#### 疑点 5（低可能）：pipelineLog 事件指向已移除的 LiveActivityPanel

- `FlowPage.h:105-106`：`m_activityPanel = nullptr`、`m_reasoningPanel = nullptr`（已移除）。
- `FlowPage.cpp:809` 的 `onPipelineLog` 检查后直接 return —— `pipeline:log` 事件被静默丢弃，不影响执行本身，但增加排查难度。

### 修复方向

**主攻疑点 1**（最可能且修复明确）：

- 方案 A（推荐）：扩展 `targetProfileResolver.js:19` 的 DVWA 识别逻辑，将 `172.17.0.2`（或更一般地，配置的靶场 IP 段）识别为 `dvwa` 类。
- 方案 B：在 `executionEngine.js:222` 查询 `metadata` 列并提取 `dvwa_profile`，传给 `buildContextForTarget(targetProfile, dvwaProfile)`。
- 方案 C：在相关 playbook 中显式设置 `dvwa_profile.base_url`。

**辅助确认**：复现时先看后端日志，确认失败步骤是哪一步、工具收到的实际命令是什么，以区分疑点 1（变量未解析）与疑点 3（容器/镜像缺失）。

## 问题二：网络拓扑功能未启动 🟡

### 现象

网络拓扑功能"并没有启动"。CLAUDE.md 标注该模块 ❌ 未实现，但实际是"大部分已实现，数据源链路在最后一环断裂"。

### 根因

#### 主因：创建扫描后不触发执行（数据源链路断裂）

```
TopologyPage 点"创建扫描"
  → POST /api/scan-tasks                    [TopologyPage.cpp:750]  ← 只创建，不执行
  → 任务以 status=PENDING 入库              [scans.js:31-50]
  → ❌ 从不调用 POST /api/scan-tasks/:id/execute
  → 扫描永驻 PENDING，无 scan_results
  → "生成拓扑"按钮启用条件需"已完成"        [TopologyPage.cpp:1260]  ← 永不满足
  → 按钮灰色，用户感知"功能没启动"
```

对比同级的 ScanPage（脆弱性扫描 Tab）：`ScanPage.cpp:1001` 创建后紧接着 `:1022` 调 `POST /api/scan-tasks/{id}/execute` 自动执行（注释 `:941` 明写 "Create scan (auto-execute)"）。**TopologyPage 缺这第二跳**。

#### 次因：无顶级导航入口

- `MainWindow.cpp:62-66`：侧边栏只有 3 个一级模块（测试任务 / 预案与知识库 / 系统管理），**没有"网络拓扑"顶级项**。
- TopologyPage 被埋在 `FlowPage` 工作台的阶段 Tab 里（`FlowPage.cpp:274`），需"侧边栏测试任务 → 双击某条流水线 → 点网络拓扑 Tab"才能到达。若无流水线，工作台不可达。
- 与 CLAUDE.md 声称的"7 个一级模块"不符。

#### 已确认正常的环节

- 后端 `POST /api/topology/generate-from-scan`（`topology.js:203-309`）是真实实现（规则提取 + LLM 增强 + 回退），非 stub/501。
- 前端 `renderTopologyScene`（`TopologyPage.cpp:1551-1662`）是真实 QGraphicsScene 渲染，非空壳。
- `graphBuilder.js` 构建的是攻击图（被 `runs.js:128` 调用），与拓扑链路无关，不是断点。

### 修复方向

- **最小修复**：在 `TopologyPage.cpp:750` 创建扫描成功回调里，仿照 `ScanPage.cpp:1022`，追加 `m_api->post("/api/scan-tasks/" + scanTaskId + "/execute", ...)`，让创建即执行。扫描跑完 → 产生 scan_results → 置 COMPLETED → "生成拓扑"按钮启用，整条链路打通。
- **可选改进**：在 MainWindow 侧边栏为"网络拓扑"加顶级入口，与 7 模块设计对齐。

## 问题三：评分界面未定位到当前任务 🟡

### 现象

执行评分界面打开后，没有自动定位到刚刚执行的任务，而是展示构造时加载的"列表第 0 条"（构造时刻最新的一条 run）。

### 根因（三个断点）

`EvaluatePage` 唯一能"定位到指定 run"的入口是 `showRun(runId)`，但该入口**只在 pipeline 完成事件路径**上被调用。从 `ExecutionPage` 直接执行任务时，传递链整条断开。

#### 断点 ①：ExecutionPage 完成时不发信号

- `ExecutionPage.h` **没有 `signals:` 段**（整文件）。
- `ExecutionPage.cpp:994-1000`：`onPollRunning` 到达终态时清空 `m_runningRunId` 并调 `onRefreshRuns()`，**不 emit 任何信号**。
- `m_runningRunId`（`ExecutionPage.h:78`）是 private，外部读不到。

#### 断点 ②：run:complete WS 事件未接到 EvaluatePage

后端 `executionEngine.js:792-801` 广播 `run:complete`（带 `run_id`），`WsClient.cpp:158` 正确分发到 `runCompleted` 信号，但 `MainWindow.cpp:185,198,217,225` 的 connect 组只接到：
- `LiveActivityPanel::onRunCompleted`
- `FlowPage::refreshFlows`（只刷 pipeline 列表，`FlowPage.cpp:326-329`）
- `ExecutionPage::onRefreshRuns`
- `ToastOverlay::onRunCompleted`

**没有任何一条接到 `EvaluatePage::showRun`**。

#### 断点 ③：Stage Tab 切换无刷新

`FlowPage` 的 `m_stageTabs` **无 `currentChanged` 处理**（全文无匹配），手切到"测试评估"Tab 不触发刷新/重选，EvaluatePage 按构造时 stale 状态展示。

#### 对比：pipeline 路径是通的

```
backend pipeline:status(completed, run_id)
  → WsClient::pipelineStatus           (WsClient.cpp:172)
  → FlowPage::onPipelineStatus         (FlowPage.cpp:761)
  → m_stageTabs->setCurrentIndex(3)    (FlowPage.cpp:776)
  → m_evalTab->showRun(runId)          (FlowPage.cpp:777)  ✅
```

### 修复方向

三处断点任补一处即可让直接执行路径通起来，推荐组合修复：

- **断点 ①**：给 `ExecutionPage` 加 `signals: void runCompleted(int runId)`，在 `onPollRunning` 终态时 emit；`MainWindow` 把它接到 `EvaluatePage::showRun`。
- **断点 ②**：在 `MainWindow.cpp:185-225` 的 `runCompleted` connect 组里追加一条 `EvaluatePage::showRun`（或经 `FlowPage` 转发）。
- **断点 ③**：给 `m_stageTabs` 加 `currentChanged` 处理，切到评估 Tab 时若已知当前 runId 则 `showRun`。
- **配套**：`EvaluatePage::setTarget`（`EvaluatePage.cpp:33-36`）当前是 no-op（`// TODO: 按 pipeline run 过滤`），可顺带实现。

## 解决顺序建议

### 第一步：确认问题一根因（先诊断，再动手）

问题一是阻塞项，且有 3 个高可能疑点（疑点 1/2/3），修复方向不同。**先复现一次并看后端日志**，确认到底是哪一条：

- 若日志显示工具命令含 `{{sqli_url}}` / `{{dvwa_cookie}}` 未解析 → **疑点 1**（DVWA 上下文）
- 若日志显示 "image not found" 或 spawn ENOENT → **疑点 3**（容器/镜像）
- 若 pipeline 停在 `awaiting_approval` → **疑点 2**（审批门，非真失败）

### 第二步：修问题一（阻塞项）

按诊断结果对症下药。最可能是疑点 1，修复点在 `targetProfileResolver.js:19` 或 `executionEngine.js:222`。

### 第三步：修问题二（一行修复，立刻见效）

`TopologyPage.cpp:750` 创建扫描成功回调里追加一次 `POST /api/scan-tasks/:id/execute`，仿 `ScanPage.cpp:1022`。修复成本极低，收益是整条拓扑链路打通。

### 第四步：修问题三（信号接线）

按断点 ①+② 组合修复：给 `ExecutionPage` 加 `runCompleted` 信号，`MainWindow` 接到 `EvaluatePage::showRun`。问题三不影响执行本身，优先级最低，可与问题二并行。

### 依赖关系

```
问题一（阻塞） ── 必须先通，否则后续无从验证
   ↓
问题二（拓扑链路） ── 独立，一行修复
问题三（评分定位） ── 独立，信号接线
```

问题二与问题三相互独立，可并行推进；问题一是阻塞项，必须先解决。
