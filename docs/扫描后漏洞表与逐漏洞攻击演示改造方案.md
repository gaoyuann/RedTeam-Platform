# 扫描后漏洞表与逐漏洞攻击演示改造方案

> 讨论稿｜2026-10-20
> 用途：供项目组讨论演示流程和开发范围。
> 本文区分现有实现与拟议改造，不表示新增功能已完成或真实靶场已验收。

## 1. 核心结论

建议将演示主流程从“扫描后执行整套预案”，调整为：

**创建任务 → 扫描 → 漏洞表 → 逐条攻击验证 → 结果回填 → 统计报告 → 环境恢复。**

漏洞表应成为扫描完成后的主操作页面。用户选择哪条漏洞，就针对哪条漏洞准备载荷、执行测试并查看效果。

底层继续复用现有预案执行器，但将预案作为单条漏洞测试的内部步骤组织方式。原有整套预案执行保留为独立的综合测试入口，不再作为演示主流程的默认下一步。

本次改造的重点是改变任务组织方式和界面动线，而不是重新开发全部扫描、载荷和执行能力。

## 2. 为什么需要改变现有流程

### 2.1 现有主流程

当前主流程侧重：

```text
扫描目标
   ↓
推荐或生成预案
   ↓
执行预案中的多个步骤
   ↓
查看整体结果
```

这种方式适合演示完整攻击链，但观众不容易对应：

- 扫描究竟发现了哪几条漏洞；
- 当前执行步骤是在测试哪条漏洞；
- 每条漏洞使用了什么载荷；
- 哪些漏洞测试过、哪些尚未测试；
- 执行完成后，到底哪些漏洞验证成立。

### 2.2 目标主流程

```text
创建任务并确认测试范围
           ↓
扫描：显示进度和完成状态
           ↓
漏洞表：呈现全部候选发现
           ↓
选择一条漏洞
           ↓
匹配已有载荷；无适用载荷时生成
           ↓
查看测试摘要并开始验证
           ↓
展示观察、证据和结论
           ↓
回填该行，继续选择下一条漏洞
           ↓
统一统计、生成报告、恢复环境
```

**扫描结束后必须停在漏洞表，等待用户选择测试对象，不自动进入整套攻击预案执行。**

扫描工具本身的探测请求仍属于扫描阶段，应遵循任务范围和扫描配置；这里的“等待选择”指扫描之后的独立攻击验证阶段。

## 3. 源码现状与复用边界

| 模块 | 现有实现 | 本次调整方向 |
| --- | --- | --- |
| 扫描结果 | 已有结果展示、稳定发现 ID、匹配载荷入口 | 将漏洞表提升为扫描完成后的主工作区 |
| 逐漏洞验证 | 已有单漏洞窗口、方案选择、载荷绑定、尝试记录、证据和人工复核 | 接入默认任务主流程，减少页面跳转 |
| 载荷库 | 已有按漏洞上下文匹配、模型生成、结构校验、保存和复用 | 统一来源标记、生成状态及错误反馈 |
| 执行器 | 已有步骤执行、超时、取消、状态和证据机制 | 用于执行单条漏洞的限定验证步骤 |
| 自动判据 | 逐漏洞入口已有响应头、Cookie 属性、目录索引等判据 | 补齐选定演示漏洞的效果判据 |
| 统计报告 | 已有实例归并、验证统计、基准导入和冻结报告 | 面向演示调整字段、布局和结论展示 |
| 拓扑 | 已有按任务扫描证据生成拓扑和节点操作 | 作为漏洞表的辅助视图，迁移后重新探测 |
| 加密狗 | 已有启动验证和运行中校验 | 保留，补最终演示设备验收 |
| 靶场管理 | 已有启动、停止和自检 | 增加恢复到指定测试基线的完整流程 |

注意：已有接口、代码和隔离测试不代表在线模型、真实工具、硬件和靶场组合已经验收。

## 4. 漏洞表设计

### 4.1 建议字段

| 字段 | 展示内容 |
| --- | --- |
| 编号 | 本任务内展示序号，并保留稳定发现 ID |
| 漏洞名称 | 扫描发现名称及必要的规则／CVE／CWE 信息 |
| 目标与位置 | 主机、服务、URL、参数或源码位置 |
| 严重性 | 扫描工具给出的严重性标签 |
| 载荷情况 | 待匹配、已有可用、本轮生成、仅参考或缺少条件 |
| 测试状态 | 未测试、准备中、执行中、取消中、已完成、执行失败、停止未知 |
| 验证结论 | 待判定、验证成立、未验证成立、证据不足、误报 |
| 操作 | 查看详情、准备测试、开始测试、查看证据、重新测试 |

表内首先展示的是“扫描发现的漏洞候选”，不能把未验证记录直接标为攻击成功。

主机信息、开放端口、扫描错误与普通提示分区展示，不混入漏洞数量。扫描部分失败时保留已获得的结果，同时显示覆盖不足的原因。

### 4.2 首版的记录粒度

首版建议沿用稳定的 `scan_results.id` 作为单条验证入口，避免改写现有验证关系。

重复发现可以增加分组或重复提示，但不得静默合并、删除原始发现。统计侧沿用已有保守归并机制，明确区分“候选记录数”“已归并实例数”和“未归并记录数”。

后续若将主表改为实例视图，一条实例必须可展开其原始发现，并明确当前测试对应哪条发现、哪个入口和参数。

### 4.3 页面布局

建议沿用 Qt Widgets，采用“漏洞表 + 详情区”布局：

```text
任务名称 / 目标范围 / 扫描状态 / 统计摘要
-------------------------------------------------------
漏洞表                         所选漏洞详情
                               · 位置和扫描依据
                               · 载荷和测试步骤
                               · 执行状态
                               · 观察与证据
                               · 验证结论
-------------------------------------------------------
扫描概况 / 拓扑 / 统计报告
```

正常使用不要求用户离开漏洞表，再去预案中心选择一套完整攻击链。技术日志保留，但折叠为详细信息。

## 5. 单条漏洞如何执行

### 5.1 操作步骤

1. 用户在漏洞表选择一条记录。
2. 系统加载该漏洞的位置、扫描依据及已有验证历史。
3. 匹配适用的测试模板和载荷。
4. 无适用载荷时，由用户点击生成，完成结构校验后保存。
5. 展示测试摘要：目标、步骤、载荷、预期证据、判定条件和清理要求。
6. 用户确认后执行，过程始终关联当前漏洞。
7. 展示证据并形成自动结论，或提示人工复核。
8. 将状态和结论回填原行，用户继续测试下一条。

查看漏洞、加载推荐和预览步骤不能自动触发模型生成或攻击执行。

### 5.2 与现有预案的关系

单漏洞测试可能仍需要多个步骤，例如：

```text
准备测试会话 → 获取正常对照 → 发起验证 → 收集证据 → 判定结果
```

这些步骤可以复用现有预案结构和执行器，但必须满足：

- 一个验证计划明确关联一条漏洞发现；
- 目标、入口及参数与该漏洞一致；
- 不附带与当前漏洞无关的横向扫描或攻击步骤；
- 每次重试保留独立尝试记录；
- 修改步骤、载荷或目标后，原确认失效；
- 开始前检查条件，停止状态未知时禁止直接重试或恢复环境。

因此，预案仍然存在，但在界面上主要表现为“当前漏洞的测试步骤”。综合预案执行继续作为独立功能保留。

### 5.3 状态与结论分开

“执行完成”只表示步骤结束，不等于漏洞成立。

例如：

- 步骤完成且证据满足判据：验证成立；
- 步骤完成但没有对应自动判据：待人工复核；
- 响应截断、入口错配或缺少对照：证据不足；
- 工具失败或停止未知：显示执行异常，不据此宣布目标安全。

## 6. 载荷生成与复用

### 6.1 建议流程

```text
读取漏洞上下文
      ↓
检索适用载荷
      ├─ 有兼容载荷 → 预览并绑定
      └─ 无兼容载荷 → 用户发起生成 → 校验 → 保存 → 预览并绑定
```

生成成功并通过结构校验后即可保存，实际测试结果另行记录。不能因为载荷已保存，就标记为已验证有效。

部分检查直接使用模板内置请求，不需要独立载荷；此时应标为“内置检查”，不能强行显示为缺少载荷。

静态参考样本与可执行结构化载荷也应区分，不能把展示命令直接当作已可执行输入。

### 6.2 新旧载荷的显示规则

建议保留两个独立属性：

- **来源**：预置库、AI 生成等，长期保留；
- **本轮使用方式**：本轮新生成、已有复用，决定显示颜色。

例如：

- 蓝色 + “已有载荷”；
- 橙色 + “本轮生成”；
- 灰色 + “待匹配／待生成”。

“本轮”首版定义为当前演示任务。下一轮新建任务时，从库中匹配到的载荷显示为已有复用，历史 AI 来源仍然保留。若需要在同一任务内开展多轮演示，需再增加明确的轮次标识。

当前逐漏洞入口采用验证项历史事件判断“本次生成”，与上述任务轮次语义不完全一致，需要统一。

### 6.3 生成过程与失败处理

展示真实业务阶段即可：

**检索载荷库 → 模型生成 → 结构校验 → 保存完成。**

无需展示模型思考过程，也不伪造百分比。需要统一扫描页与逐漏洞窗口的超时处理，并支持查询处理结果，避免界面超时后重复生成。

首版继续复用项目自己的模型客户端，无需为演示引入独立 HexStrike 服务。

## 7. 如何展示攻击效果

首版建议选定 2～3 个固定、可重复的隔离靶场案例，逐个打通，不承诺任意漏洞都能自动攻击和判定。

每个案例必须明确：

| 内容 | 要求 |
| --- | --- |
| 测试前提 | 靶场版本、测试入口、必要会话与配置 |
| 正常对照 | 未触发漏洞时的可观察行为 |
| 测试观察 | 对应当前漏洞的实际返回或受控效果 |
| 成立判据 | 什么证据足以支持漏洞成立 |
| 不成立／不足 | 阴性结果、缺条件、超时和证据不完整如何区分 |
| 恢复方式 | 测试后如何返回基线 |

例如，SQL 注入案例可展示隔离靶场中预置测试数据的访问差异；目录暴露案例可展示测试目录的索引暴露。只展示与验证有关的必要内容，不将真实敏感数据作为演示素材。

当前逐漏洞自动判据偏向配置缺陷检查。选择利用型案例后，需要单独补充对应的判据和效果展示，不能直接把现有工具成功状态当作漏洞成立。

## 8. 统计与报告

建议主展示区突出：

1. 应有漏洞数；
2. 已发现漏洞数；
3. 已测试漏洞数；
4. 验证成立数；
5. 待验证和证据不足数量。

其中：

- “应有漏洞数”来自对应靶场版本的已知漏洞基准；
- “已发现漏洞数”必须说明是匹配基准的数量，还是已归并实例数；
- “已测试漏洞数”按实际执行验证的实例计数，不按工具调用次数；
- “验证成立数”必须关联具体尝试和证据；
- 没有可靠基准时显示“未知”，不反推分母、不编造发现率；
- 误报、未验证成立和证据不足分别呈现，不统一归为失败。

报告应包含任务范围、环境版本、扫描覆盖、逐漏洞结果、证据引用和限制说明。继续复用现有冻结快照机制，历史报告不随后续重试变化。

页面详情应转为可读字段，避免直接向演示观众展示原始 JSON。

## 9. 环境恢复与迁移

### 9.1 环境恢复

当前靶场启动、停止、自检不等于恢复到测试前基线。需要补充：

```text
核实执行已停止
      ↓
恢复测试数据、配置及必要文件
      ↓
健康检查
      ↓
核对基准版本
      ↓
允许下一轮测试
```

恢复对象是被测环境。平台中的载荷库、证据、验证历史和报告继续保留，以便展示第二轮复用。

恢复失败或调用停止未知时，显示明确原因并阻止开始下一轮。首版只实现选定演示靶场的恢复方式，不承诺通用虚拟机或容器恢复。

### 9.2 迁移部署

建议先采用：

**Qt 客户端 → 服务器后端与工具 → 隔离靶机。**

客户端连接远端后端，不等于已经支持任意远端执行代理。当前任务范围中的远端执行位置仍有未接通限制，应按实际工具所在位置设计演示网络。

更换机器、网段或执行位置后重新扫描并生成拓扑，不直接把历史拓扑当作当前环境事实。三个目录可以组织交付包，但目录本身不提供隔离或环境恢复能力。

源码检测可作为独立演示场景接入同样的漏洞表。现有 CScan 路径可复用，但源码候选进入动态测试前必须具备明确的运行入口和触发条件。

## 10. 分阶段实施建议

| 阶段 | 主要工作 | 完成标志 |
| --- | --- | --- |
| 第一阶段：改主流程 | 扫描完成停留漏洞表；单条测试入口成为主要操作；保留综合预案入口 | 用户能从表中完成一条漏洞测试并回填结果 |
| 第二阶段：补效果闭环 | 为选定案例完善模板、载荷、对照、证据和判据；统一生成超时与新旧标记 | 典型案例能展示清晰、可复核的结果 |
| 第三阶段：补重复演示 | 实现固定靶场恢复；第二轮复用载荷；完善失败状态 | 恢复后可再次执行，不依赖手工清库 |
| 第四阶段：完善展示与迁移 | 调整统计报告、实际缩放下的页面布局、目标设备部署 | 在最终演示环境连续完成 2～3 轮验收 |

首版不必引入并发批量攻击。先将逐条流程跑通，再考虑勾选后按顺序执行；批量执行也必须保留每条漏洞独立的条件检查、尝试和结论。

## 11. 验收标准

- [ ] 扫描完成后进入漏洞表，不自动执行整套攻击预案。
- [ ] 漏洞、资产信息与扫描错误清楚区分，部分失败不会丢失已有结果。
- [ ] 点击一条漏洞，只准备和执行该漏洞范围内的测试。
- [ ] 打开详情和查看推荐不会自动调用模型或攻击目标。
- [ ] 有适用载荷时复用，无适用载荷时可显式生成。
- [ ] 新生成载荷保存后可再次找到，下一轮正确显示为已有复用。
- [ ] 界面超时、重复点击不会造成重复执行或混乱绑定。
- [ ] 每条测试展示目标、载荷、观察、证据及结论。
- [ ] 执行完成不直接等于漏洞成立，人工复核保留历史。
- [ ] 取消后核实实际停止；停止未知时不能立即重试或恢复环境。
- [ ] 统计与逐条记录一致，已知基准和未知分母显示正确。
- [ ] 恢复靶场后可再次测试，平台证据和载荷库保留。
- [ ] 最终演示设备上完成加密狗、拓扑、工具和模型联调。
- [ ] 连续完成 2～3 轮演示，记录失败、恢复情况及结果差异原因。

## 12. 建议与师兄确认的问题

1. 是否同意将“漏洞表逐条测试”设为默认主流程，综合预案执行保留为独立入口？
2. 首轮具体演示哪 2～3 类漏洞、使用哪个靶场版本？
3. “攻击效果”希望展示到什么程度：验证成立、受控数据访问差异，还是其他明确效果？
4. 首版是否接受未覆盖自动判据的漏洞由人工复核？
5. 是否按“一轮演示一个新任务”定义载荷的新旧颜色和统计范围？

这些选择确定后，才能按具体案例估算开发工作量和安排真实环境验收。
