## 一、硬件与角色定义

### 1.1 硬件配置

| 设备 | 数量 | 架构 | 关键规格 | 角色 |
|------|------|------|---------|------|
| 便携式 AI 算力主站 | 1 | x86 (海光) | 2×RTX 4090 + 1×Tesla T4, 320GB RAM, 8TB SSD, 12路PoE | 服务器 |

### 1.2 需求规格书硬件定义

> "信息系统安全智能化测试平台硬件由**服务器**、**攻击测试端**、**防御测试端**和**测试控制端**（安装'信息系统安全智能化测试软件'）组成"

**关键理解**：
- **测试控制端**安装完整软件，拥有全部功能（管理员全景视图）
- **攻击测试端**是受限的操作员视角（侦察+扫描+攻击）
- 控制端 ⊃ 攻击端（控制端包含攻击端所有功能 + 管理功能）

## 三、六大改造方面

### 3.1 网络架构：单机 → C/S

**现状**：`app.listen(PORT)` 绑定 `127.0.0.1`，前端硬连 `http://127.0.0.1:3002`

**改造**：
- 后端绑定 `0.0.0.0:3002`（或服务器局域网 IP）
- 前端 `ApiClient` 的服务器地址改为**可配置**（登录界面输入服务器IP，或配置文件）
- `start.sh` 拆分为 `start-server.sh`（服务器端）和 `start-client.sh`（客户端）
- 服务器端启动：Node.js backend + SQLite + Podman/Docker daemon
- 客户端启动：仅 Qt 前端二进制

### 3.2 多用户 + 角色权限（RBAC）

**现状**：有 LoginDialog 但无真正的认证/授权，无角色区分

**改造**：
- 后端增加 JWT 认证中间件（登录 → 发 token → 后续请求带 token）
- 数据库增加 `role` 字段：`admin`（控制端）/ `operator`（攻击端）/ `defender`（防御端）
- 后端路由增加角色守卫：攻击端用户调 `/api/config` → 403
- 前端根据角色动态显示/隐藏模块导航项
- 口令必须改为 bcrypt 加密存储（当前明文是安全缺陷）

### 3.3 跨架构编译与国产化适配

**现状**：x86_64 + WSL2 开发，Qt5 编译产物是 x86

**改造**：
- **服务器端**（x86 海光）：当前代码直接可用，无需改动
- **客户端**（ARM64 飞腾 + 银河麒麟/UOS）：
  - **推荐方案**：在云笔电上原生编译 Qt5 前端（云笔电预装银河麒麟开发环境）
  - 备选：交叉编译（x86 开发机上用 `aarch64-linux-gnu-g++`）
- 容器镜像仅需 `linux/amd64`（工具容器跑在服务器上，客户端不需要容器）

### 3.4 实时通信：多终端协同

**现状**：纯 HTTP 请求-响应，无推送能力

**改造**：
- 后端增加 **WebSocket**（`ws` 或 `socket.io`）：
  - 攻击端发起扫描 → 控制端实时看到扫描进度和结果
  - 攻击端执行 Playbook → 控制端实时看到执行日志
  - 服务器端容器状态变更 → 所有终端收到通知
- 前端 Qt 用 `QWebSocket` 接收推送

### 3.5 AI/LLM 服务集成

**现状**：1 个 DeepSeek LLM 调用（Playbook 生成），远程 API

**改造**：
- 服务器有 2×RTX 4090 + 1×Tesla T4，应跑**本地 LLM 推理服务**（vLLM / Ollama）
- 后端调用本地 LLM（`http://localhost:11434` 或 vLLM 端口），不依赖外网
- LLM 用途扩展：智能 Playbook 生成 + 扫描结果分析 + 攻击建议 + 报告自动生成
- 云笔电不跑 LLM，只通过后端 API 间接使用

### 3.6 部署模式：固定式 + 移动式

**现状**：`start.sh` 单机一键启动

**改造**：
- **固定式（实验室）**：服务器常驻运行后端，8台云笔电开机连服务器
- **移动式（现场）**：服务器便携（本来就是"便携式AI算力主站"），到现场后 PoE 供电启动，云笔电通过有线网连接
- 服务器端 `start-server.sh`：启动 Docker/Podman → 启动 LLM → 启动 Node.js backend
- 客户端 `start-client.sh`：仅启动 Qt 前端（可配服务器地址）

## 四、改造优先级

| 优先级 | 改造项 | 原因 | 预估工作量 |
|--------|--------|------|-----------|
| **P0** | 网络架构 C/S 分离 | 所有其他改造的前提 | 1-2天 |
| **P0** | 多用户认证 + RBAC | 多终端连同一服务器，必须区分身份和权限 | 3-5天 |
| **P1** | 前端角色化 UI | 有了 RBAC 后前端才能按角色显示不同模块 | 2-3天 |
| **P1** | WebSocket 实时推送 | 多终端协同的核心体验 | 3-5天 |
| **P1** | 跨架构编译（ARM64） | 云笔电是飞腾 ARM64，前端必须能跑 | 2-3天(调试) |
| **P2** | 本地 LLM 集成 | 服务器有 GPU，应充分利用 | 3-5天 |
| **P2** | 部署脚本拆分 | 固定式/移动式两种模式 | 1天 |

## 六、核心原则

1. **后端 API 基本不变** — 改造是架构升级，不是推倒重来
2. **容器/工具在服务器执行** — 云笔电只发指令、看结果
3. **数据库在服务器** — 云笔电不存数据，所有操作经后端 API
4. **SQLite 在 C/S 下可行** — 单进程（后端）写 SQLite，多终端并发读经 API
5. **控制端 ⊃ 攻击端** — 控制端拥有全部功能，攻击端是受限子集
6. **防御端暂不实现** — 当前功能完全缺失，合理延后
