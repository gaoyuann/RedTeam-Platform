## 3. 验收前准备与基线冻结

### 3.1 保存代码与构建基线

在仓库根目录执行，保存完整输出到本次验收记录：

    git rev-parse HEAD
    git status --short
    git diff --check
    JWT_SECRET=acceptance-fixture npm --prefix backend test
    cmake -S . -B build -DBUILD_UI_CHECKS=ON
    cmake --build build -j2
    ctest --test-dir build -R 'ui-context-' --output-on-failure

后端测试、构建、CTest 或补丁格式任一失败时，停止人工验收并记录为“代码基线不通过”。Qt 弃用警告应记录；只要不造成构建或测试失败，不作为本轮阻断项。

### 3.2 准备人工验收数据

1. 准备三个测试身份：任务所有者 A、非所有者 B、管理员 Admin。
2. 使用明确授权的测试目标和独立验收任务，避免复用运行中的任务或来源不明的历史记录。
3. 准备三类可复用扫描证据：配置类、目录或入口类、带具体参数的 SQL 注入线索类。可使用隔离测试数据或已完成的授权扫描。
4. 记录后端健康状态、客户端程序版本、实际 API 地址和实时状态通道。启用 WebSocket 时记录连接状态；未启用时记录 HTTP 轮询状态。
5. 不使用真实业务凭据、生产数据或未授权目标作为验收输入。

## 6. C：任务闭环与 UI

### 6.1 主闭环

1. 用 A 创建完整任务，填写任务名称、授权范围、目标和执行确认策略。
2. 从任务概览依次进入扫描、智能分析、预案、执行、结果/报告工作区。
3. 提交预案后，用 Admin 审批，再回到 A 的执行视图。
4. 生成结果报告、提交报告审阅并导出 JSON 和 HTML。

| 编号 | 预期结果 |
| --- | --- |
| C-01 | 六阶段显示为准备、扫描、分析、预案、执行、评估，当前阶段与任务状态一致。 |
| C-02 | 所有工作区显示同一个任务、目标、授权范围和阶段；日志、AI 面板、执行与结果引用同一上下文。 |
| C-03 | 扫描事实、AI 候选、验证证据和正式结论有明确区分；候选风险不会直接显示为已验证漏洞。 |
| C-04 | 预案保存后版本递增；普通用户可提审，只有 Admin 可批准；批准快照与实际执行预案一致。 |
| C-05 | 报告为来源冻结快照，包含预案版本、Run 和证据来源；审阅版本独立递增，任务所有者不能自审。 |
| C-06 | JSON 与 HTML 导出和冻结报告一致；不支持格式有明确拒绝说明。 |

## 10. 当前能力边界

- 全局搜索、通知中心、CVE 实时知识源和跨任务风险排名不属于本轮验收功能。
- 报告是可审阅的草稿和冻结快照，不等同于正式漏洞裁决、不可篡改证据库或 PDF/Word 全量交付。
- 授权范围文本、审批和条件校验已进入流程，但不是完整网络级策略执行系统。
- 拓扑依据扫描证据展示逻辑关系，不等同于交换机端口、VLAN 或物理布线发现。
- 自动化回归使用内存数据库、回环 HTTP、假工具或受控夹具；它不能替代真实部署、模型服务、工具容器和授权任务的人工验收。

判定规则：

1. A 至 F 的阻断项均未出现，且每项都有可复核证据，结果为通过。
2. 功能符合设计但受当前环境限制时，结果为受限，并写明替代路径和后续条件；不能直接记为通过。
