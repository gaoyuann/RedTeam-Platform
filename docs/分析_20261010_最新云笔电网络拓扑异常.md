## 结论

最新结果不存在已证实的 `.103/.112/.111` IP 互换或悬空链路端点。用最新数据库的实际记录重放部署版本，生成的节点、边与云笔电缓存完全一致。

主要问题是：**把设备、任务角色、服务和逻辑网段放在同一张图中表达，名称采集及名称展示又不完整；服务 Banner 的系统信息还被直接提升成主机系统信息。** 因此结果看起来像真实设备拓扑，但实际只是“请求来源 + 扫描路径 + 同网段分组”的组合视图。

## 已确认的问题与原因

### 1. 三种关系混画，造成链路错乱的观感

最新图有 13 个节点、14 条边：

| 关系 | 数量 | 实际含义 |
| --- | ---: | --- |
| `route` | 1 | Nmap 从扫描执行端 `.103` 到 `.111` 的第一跳响应 |
| `task-request` | 1 | 云笔电 `.112` 向服务器 `.103` 发起 HTTP 任务请求 |
| `virtual-link` | 12 | 节点属于 `192.168.1.0/24` 的逻辑分组 |

“虚拟交换机”节点没有 IP，类型为 `network_segment`，不是发现的实体交换机。其 12 条连线包括扫描服务器和 11 个 ARP 响应地址。Nmap 本次只发现 11 个响应地址，并没有发现实体交换机或端口布线。

局域网分组生成位于部署版本 `backend/src/services/topologyBuilder.js:314`；固定分栏坐标位于同文件 `:332`；前端直线绘制和中点标签位于 `frontend/src/pages/TopologyPage.cpp:2031`。

根据本次实际节点坐标，`.103 → .111` 的路径中心线与两条逻辑分组连线相交，交点约为 `(656,459)` 和 `(224,51)`。前端没有避让路由或连线标签布局。边类型虽然使用实线、虚线、点划线区分，但仍在同一画布叠加，不代表真实物理连接。

**判断：本次路径端点正确，关系表达与布局存在问题；不能把交叉线当作连接节点，也不能把同网段分组当成物理交换机连接。**

### 2. 主机名采集被禁用，已识别的服务名称又被丢弃

局域网发现实际命令参数为：

```text
-sn -n --reason -e enx0826ae3bd7fa --max-retries 1 192.168.1.0/24
```

`-n` 禁用 DNS 解析，`-sn` 只做主机发现，不识别各邻居的应用服务。因此这轮 LAN 结果中的 `hostName` 全为空，不能据此可靠给 `.100/.102/.104/.105/.106/.107/.108/.113` 命名。

即使 Nmap 返回主机名，后端 `nodeFor` 仍将 `displayName` 初始化为 IP，后续只更新 `hostName`；前端 `topologyNodePrimaryLabel` 优先展示非空 `displayName`。已用带主机名的 Nmap 样本复现：`hostName=real-host.example`，卡片主标题仍选择 `192.0.2.10`。

对应部署代码：

- `backend/src/services/scanExecutor.js:880`：LAN 发现使用 `-n`。
- `backend/src/services/topologyBuilder.js:42`：默认显示名为地址。
- `backend/src/services/topologyBuilder.js:103`：仅更新 `hostName`。
- `frontend/src/pages/TopologyPage.cpp:536`：主标题优先使用 `displayName`。

本次 HTTP 结果 `id=339` 和 `id=341` 已明确给出：

```text
http://192.168.1.111:4280/
Welcome :: Damn Vulnerable Web Application (DVWA)
```

但是 `http_probe` 和 `technology_detection` 在拓扑构建循环中只用于定位节点，没有把标题、应用指纹合并进服务展示；所以图中仍是 `.111` 和 `http/Apache`，看不到 DVWA。对应 `backend/src/services/topologyBuilder.js:91`、`:129`。

**判断：有部分名称信息已经扫描出来但没进入拓扑；其他邻居的名称根本没有采集，不能靠任意猜测补齐。DVWA 是 `.111:4280` 的服务名，不宜直接当成整台 `.111` 的唯一设备名，该 IP 还承载其他靶场服务。**

### 3. “源主机/服务器”是任务角色，不是系统主机名

任务保存的来源记录为：

```text
sourceAddress = 192.168.1.112
serverAddress = 192.168.1.103
capturedAt = 2026-10-10T12:14:47.043Z
```

因此当前正确关系为：

| 地址 | 已验证角色 | 名称说明 |
| --- | --- | --- |
| `.112` | 云笔电，任务请求发起端 | 系统主机名为 `user4`；图中固定显示“源主机” |
| `.103` | 后端服务器、Nmap 执行端 | 系统主机名为 `aistation2`；图中固定显示“服务器” |
| `.111:4280` | 本次 DVWA 服务目标 | 服务标题明确识别 DVWA；设备名没有从扫描取得 |
| `.113` | 本次 LAN 发现的邻居 | 不代表本任务已识别其所有服务或将其作为攻击目标 |

“源主机”来自 HTTP socket 来源，不是发出 Nmap 探测包的主机。本次扫描由服务器 `.103` 执行，`.112` 只提交任务。对应 `backend/src/services/topologyBuilder.js:223`、`:252`、`:272`。

旧靶场说明文档记录的平台地址 `.110` 不能代替此次实际运行的 `.112`；文档与当前任务来源的地址口径也需要分开。

### 4. 服务容器系统被标成了物理主机系统

Nmap 实际服务 Banner 为：

```text
4280/tcp open http Apache httpd 2.4.68 ((Debian))
```

部署版本 `backend/src/services/topologyBuilder.js:126` 从服务字符串匹配 `Debian/Ubuntu/CentOS/Windows`，直接写入节点 `osName`，所以 `.111` 被显示为 `Debian`。

靶场资料记录 `.111` 宿主机为 Kylin Industry V10 SP1 / ARM64，并运行 Docker。Banner 中的 Debian 可能描述服务容器/软件构建环境，并不证明宿主机为 Debian。本次没有登录 `.111` 核验宿主机系统，不能以 Banner 或旧文档作本机系统的最终判定。

同一段逻辑还把 `Apache httpd 2.4.68` 拆为 `product=Apache`、`version=httpd 2.4.68`，说明文本格式拆分不够准确。

**判断：把服务指纹提升为设备属性是实际语义错误，必须区分主机系统和服务/容器系统来源。**

### 5. 较新的执行日志并不更新拓扑

`GET /api/topology/from-pipeline/:id` 只查询任务关联的 `scan_results`，以及通过 `parameters.pipeline_id` 关联的额外 `topology_scan`；不读取执行阶段的新工具证据。对应 `backend/src/routes/topology.js:56`。

所以 20:55 产生新执行日志，但拓扑仍表示 20:14–20:16 扫描结果，这是当前数据接入范围，而不是把 20:55 的网络发现完整反映到图里。

前端还有归档优先策略：恢复已有归档后直接返回，没有源结果指纹或投影版本的有效性校验。对应 `frontend/src/pages/TopologyPage.cpp:839`、`:861`。后续算法修复或同一组扫描产生新增证据时，历史图可能继续保留。

**但本次缓存与最新扫描数据重放完全一致，不能把归档陈旧认定为当前错配的直接原因。**

## 待核验的网络现象

- `.104` 与 `.106` 在此次原始 Nmap 输出中返回同一个 MAC：`00:E0:AC:36:C7:DE`。这不是前端把 MAC 放错了。可能涉及一台设备多地址、代理 ARP 或其他网络配置；仅凭这轮结果不能区分，不能直接认定为 IP 冲突，也不应自动把两项合并成同一设备。
- 默认路由配置的网关为 `.1`，但本次到 `.111` 属于直连网段且 traceroute 只有目标第一跳。`.1` 可标为“配置网关”，但没有证据把它插入 `.103 → .111` 的探测路径。
- Nmap/ARP/traceroute 不能识别所有二层交换机及物理端口连接；若目标是物理网络拓扑，需要独立的 LLDP/CDP/SNMP/FDB 等授权证据。

## 建议修复顺序

1. **拆开视图语义**：默认展示资产与逻辑网段；任务请求关系、扫描路径单独开关或分层。逻辑节点改名“局域网/逻辑网段”，明确非实体交换机，加入连线避让及标签布局。
2. **分离身份与角色**：以扫描时 IP 等观测信息建立节点；角色标签独立于设备显示名。主机名可从授权的资产登记、DNS/NetBIOS 等证据获得；不要用账户、厂商或服务标题冒充设备名。
3. **补齐服务映射**：将 HTTP 标题、技术指纹归到对应 `IP + 协议 + 端口 + URL` 服务，保留 DVWA/Pikachu/SQLi-Labs 等多服务共存信息；修正默认 IP 显示名遮盖已有主机名的逻辑。
4. **修正系统属性归属**：服务 Banner 系统只放服务属性及证据来源；无主机级证据时宿主机系统保持未知，避免把 Debian 容器标成麒麟宿主机。
5. **定义新鲜度**：展示扫描采集时间；归档保存源记录指纹和投影版本。保留人工编辑，显式提示更新。若要用执行证据补图，先定义证据类型、作用域和来源，不能把任意执行文本中的 IP 当作设备。
