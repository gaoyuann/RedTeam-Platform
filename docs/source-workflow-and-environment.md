# 源程序测试链路与环境核对

新增编译信息、独立反证复核、预案判定和实际对照测评见 [源码扫描质量增强](source-scan-quality.md)。
已有预案、任务草稿和审批执行版本的关系见 [来源预案与任务执行版本](task-plan-versions.md)。

## 操作链路

1. 新建程序测试任务，分别提供源码目录与真实的 HTTP/TCP 运行地址。源码下载地址不是程序运行地址；只有源码时可以静态分析和保存待补条件的预案，不能执行运行验证。
2. 扫描阶段保存源码快照，运行 cppcheck / Flawfinder，再按静态告警和危险操作优先审阅代码。跨文件片段按有界词法检索取得，不代表编译器验证的调用图。
3. 检查扫描发现和覆盖记录。工具失败、文件被跳过、AI 预算不足、无效定位均属于覆盖缺口；没有告警不代表安全。单个工具或模型异常保留已有结果，不会丢弃快照。
4. 在扫描发现、智能分析或任务预案页面点击“生成攻击测试预案”。依据本任务发现、实际代码、触发条件与入口响应生成步骤。可以通过选择窗口指定 1–10 条发现；每条发现使用独立的正常对照与验证步骤。
5. 生成成功后自动打开任务预案并建立草稿，显示具体步骤。页面刷新或重新进入任务后，通过本任务来源预案列表找回已生成预案。已有草稿和未保存编辑不会被新生成结果替换。
6. 审阅、保存、提交审批，由管理员批准当前版本并执行。批准后冻结步骤，执行证据保留发现 ID 和对照 / 验证阶段，便于逐项复核。来源预案保留一份，批准版本只在所属任务和历史执行中使用，不再混入通用预案库。添加“候选备注”只添加审阅意见，不会创建工具步骤。
7. 查看执行证据并复核“证据支持 / 未复现 / 条件不足”。工具执行成功、连通成功或 HTTP 200 都不能单独证明源码漏洞成立。

### 拓扑与漏洞选择

程序 / 源码扫描在完成或部分完成后都可展示已有拓扑证据。有运行入口时，展示实际入口响应及任务请求关系；网络跳点和局域网关系仍以已有网络探测证据为准。仅提供源码目录、未填写“攻击测试运行入口”时，没有程序运行连接证据，拓扑页会说明缺少运行地址，不把源码下载服务当成被测运行程序。Web 任务还包含端口与网络探测，因此其网络拓扑可能比单独的程序扫描更完整。

“选择漏洞生成预案”窗口使用显式复选框，也可点击发现行选择或取消，最多选择 10 项。普通行选中和漏洞勾选保持一致，生成按钮随勾选数量更新。只有源码的发现可以生成待补运行条件的草稿；填写真实运行入口后才可生成可执行验证步骤。明确标记缺少触发输入或正常对照的运行发现仍显示原因，不能作为可执行演示对象。

纯源码草稿明确向模型提供所选漏洞的整数 `finding_id` 和完整编号清单，并按所选数量分配输出预算。草稿漏项、重复编号、引用未选漏洞或格式错误时，最多请求一次完整纠正；再次失败会提示具体问题，不保存无效草稿。任务日志记录所选编号、失败原因及调用/纠正次数，原始源码和模型回复不写入日志。模型断线或明确返回条件不足时直接报告原因。有效草稿仍标记为不可执行，等待补充真实运行条件。

生成失败后恢复生成和漏洞选择按钮，清除旧生成结果的执行入口，再次点击会重新请求生成。任务预案页发起生成时，如果扫描详情仍在加载，会在本任务详情就绪后继续；切回 C/C++ 扫描标签也会恢复当前任务。生成过程中重复点击不会重复请求，离开任务后迟到回复不能建立草稿。10 条是每次生成的数量上限，扫描发现总数不受此限制，更多发现需分批选择。

没有可信输入点或缺少运行条件时，生成器必须说明缺什么，不能用通用目录枚举替代源码漏洞验证。旧任务无需覆盖历史记录；修复部署后，对工具未实际运行的任务新建扫描以获得完整证据。

## 环境自检与离线镜像

在扫描后端以实际后端账号执行：

```sh
cd backend
npm run check:source-env -- --source-kind http --all-images --output /tmp/source-environment.json
```

`--source-kind` 可选 `http`、`local`、`ssh`。自检采用后端同样的引擎选择顺序，检查实际镜像、CPU 架构、两个静态工具启动和目录权限；本地来源另查 Python，SSH 来源另查 SSH 客户端并列出源码主机要求。它不拉取或构建镜像，不连接模型或测试目标，不读取凭据，也不修复数据库。必需环境失败返回非零退出码，可选镜像缺失只列入清单。

离线交付时，在与扫描后端 CPU 架构相同的构建主机导出并记录校验值：

```sh
docker save rt-sast-c:latest | gzip -1 > rt-sast-c.tar.gz
sha256sum rt-sast-c.tar.gz
```

传输后核对 SHA-256，再在扫描后端以实际账号导入。若已有同名镜像，先记录原镜像 ID 并保留回退标签；本轮实验室镜像原先缺失，没有覆盖已有版本。

```sh
sha256sum rt-sast-c.tar.gz
docker load -i rt-sast-c.tar.gz
docker image inspect rt-sast-c:latest --format '{{.Id}} {{.Architecture}}'
docker run --rm --pull=never --network=none rt-sast-c:latest cppcheck --version
docker run --rm --pull=never --network=none rt-sast-c:latest flawfinder --version
```

Podman 环境将上述 `docker` 替换为 `podman`，不能把镜像导入另一引擎或另一账号后就认定后端可用。仅导入工具镜像不需要重启后端；旧扫描结果保留，新建扫描后才能取得真实工具结果。

## 拓扑与验证范围

程序/源码任务自动补充目标端口与网络拓扑探测，不依赖预案运行条件。已有任务可以在拓扑页点击“补充网络探测”，范围固定为当前任务主机。源码输入没有调用地址时也保留独立网络证据；未探测的主机显示未知状态，不将源码目录或文件读取当成程序运行、端口开放或漏洞成功证据。

程序测试默认填写 HTTP/CGI 或 TCP 服务地址，源码目录单独填写。不要求源码包含 main 函数。兼容旧任务：若目标为 HTTP 主机根地址、同源源码目录另行保存，则保留目标作为声明的程序测试地址；生成预案前缺少入口响应时先读取真实响应。源码目录本身、跨主机目录、没有单独源码目录的文件输入不会被自动认作程序入口。仅有源码文件时仍可生成验证草稿；当前 HTTP/TCP 执行器不能凭空编译部署程序或证明源码对应部署版本。

拓扑只使用本任务及本任务所有者的扫描结果。HTTP/TCP 连接响应可以建立程序入口服务和应用请求关系，不能推导物理直连、交换机或未观察到的路由。源码发现保持候选状态，不把代码和完整响应加入拓扑。

自动归档保存来源指纹和投影版本，后续扫描结果更新时可刷新未人工编辑的拓扑。人工编辑归档保留，旧归档缺少这些标记时使用页面的更新入口重新取得结果。

## 验证方式

后端全量回归：`cd backend && npm test`。真实静态工具回归：`SOURCE_TEST_SAST=1 npm test`。

Qt 界面验证：`cmake -S . -B build -DBUILD_UI_CHECKS=ON`、`cmake --build build -j2`、`ctest --test-dir build -R ui-context --output-on-failure`；拓扑另使用已有 `build/topology-ui` 冒烟检查。

本次网络/运行地址修复的本地回归：`cd backend && npm test`，249 项通过、6 项依赖外部环境而跳过。Qt 主程序及 `RedTeam-Platform-Batch16Checks` 构建通过，`ctest --test-dir build -R ui-context --output-on-failure` 三档缩放均通过，`ctest --test-dir build/topology-ui --output-on-failure` 通过。覆盖旧源码任务的实际 HTTP 响应采集与验证请求、失败后重试、源码/网络一侧失败时保留另一侧结果、无程序调用地址时仍展示网络路由，以及管理员代为探测的任务归属。上述为本地测试，不能代替云笔电与服务器的新版本部署验收。

2026-10-13 已在实验室扫描服务器的隔离目录、实际 Docker 镜像和已安装 Node.js 20.20.2 环境完成 `SOURCE_TEST_SAST=1 npm test`：242 项通过、0 失败、0 跳过。首次测试包遗漏了仓库样例和页面源码，补齐后全量通过，未删改断言。模型回复在这组回归中是受控测试回复。

另在明确授权后，用固定六行 C 样例完成真实模型全链路：真实静态检查 → AI 分析 → 独立复核 → 生成三步预案 → 找回任务来源与草稿 → 提审、批准 → 实际本地 HTTP 请求 → 三条关联证据。样例单独编译并启用诊断，每次请求运行独立子进程；两条验证证据取得实际 ASan 诊断并关联到冻结源码第 5 行，两条观察均满足预案判定。预案首次错误地将不同查询 URL 用于响应差异比较，系统拒绝并通过一次纠正获得有效判定；没有放宽范围或定位校验。

该验收使用内存数据库和临时固定样例，没有编译用户项目，没有把用户源码发送给模型。平台保留人工复核要求，不自动把诊断文本当作正式漏洞确认。真实项目的覆盖率、误报、漏报和部署版本仍需对照验收。

服务器真实静态工具对照中，Cppcheck 检出三个已知缺陷、三个修复样例无告警；Flawfinder 检出一个缺陷，漏报两个，且在一个修复样例上仍有告警。这只反映六个样例的表现，不能据此宣称真实项目达到同等精度。

正式服务保持运行、健康检查通过，没有部署未合并代码，没有重启客户端或改写正式任务。代码及页面修复仍待用户手动 PR 合并和发布，真实模型输出质量与目标程序的实际缺陷验证另行验收。

## 本次增强与实验室验收计划

本地已实现：

- 明确提供源码的程序任务先实际读取和审阅源码，再让智能体选择后续检测；只有运行地址时先观察真实入口。模型断线不会抹掉已取得的输入检查结果。
- 根据实际协议限制方法，TCP 程序不调用 HTTP 扫描器；同一方法不重复执行，预算耗尽和中途失败记录覆盖不足。
- 无效源码引用或 JSON 格式允许一次纠正，每次审计最多增加两次模型调用；所有新发现仍通过相同的快照引用校验，保留原始拒绝记录。
- 真实验收发现预案中的 `<target>/path` 不是有效 URL。生成时要求完整真实 URL，格式错误允许一次纠正，仍严格校验目标范围、发现 ID 和对照顺序；条件不足或连接失败不强行生成预案。
- 响应差异判定在生成与审批时检查前置对照的完整 URL 和请求方法，执行时按相同条件找对照。GET 查询输入变化使用实际可观察文本或状态码判定，防止生成可以执行却无法比较的预案。
- 扫描、独立复核、预案与程序决策向 DeepSeek 请求 JSON 输出约束，避免在 JSON 后附加说明导致解析失败；空回复明确报告错误。其他网关保持既有请求字段，源码证据和预案范围校验继续执行。该服务的参数要求见 [DeepSeek JSON 输出文档](https://api-docs.deepseek.com/guides/json_mode/)。
- 工具启动、输出解析和模型连接异常各自记录；源码读取失败也保存明确的未覆盖记录，不用成功的入口响应替代源码审阅。
- 已接通预案自动展示、任务草稿恢复、当前任务来源过滤、审批快照执行、发现与证据关联，并补齐任务切换时迟到响应的回归。

新增 `source-offline-workflow.test.js` 分别从 HTTP 源码辅助任务、TCP 程序任务走完整链路，实际使用 Python 源码读取、cppcheck / Flawfinder 容器、SQLite 草稿审批和真实本地请求。仅模型回复被替换为受控的测试回复，快照保存在临时目录，结束后清理。使用 `SOURCE_TEST_SAST=1 npm test` 启用这两项完整测试。

按以下顺序验收（镜像导入、环境检查与服务器隔离回归已完成，正式代码发布仍待手动 PR 合并）：

1. 恢复实验室连接，确认扫描后端与客户端实际地址、运行账号、部署版本和 CPU 架构。导入 / 构建匹配架构的 `rt-sast-c:latest`，并确认后端实际选中的容器引擎能看到该镜像。
2. 部署本次前后端修复，按既有方式备份和验证数据库迁移。核对模型可调用、源码可读取、运行入口可达。
3. 对一个真实 HTTP 程序新建任务：检查源码文件 / 哈希、两个静态工具结果、AI 定位与覆盖缺口；生成预案后应自动打开任务草稿，重新进入任务仍能看到步骤。
4. 提审并批准，核对执行实际请求地址、正常对照 / 验证输入、原始响应和发现 ID。不要只看任务完成图标。重复点击不应建立第二份草稿或覆盖已有编辑。
5. 对一个真实 TCP 程序重复流程，核对菜单前置交互、连接关闭 / 超时处理及协议专用步骤。不得出现 HTTP 扫描器任务或把源码目录端口当作运行服务。
6. 查看拓扑：运行服务端口和程序入口响应应有依据；无路由记录时不显示实际路由。检查刷新结果和人工编辑归档的保留行为。
7. 使用已知缺陷版本与修复版本作对照，记录真实模型误报、漏报、输入可达性和运行证据；补测工具缺失、模型断线、源码拒绝访问及执行取消时的提示与状态。

远端没有实际运行地址、可信输入点或诊断接口的缺陷，应记录“条件不足”，不能通过换一个通用模板或补齐无关镜像来宣称流程已完成漏洞验证。

### 预案生成与页面状态

从任务预案发起生成时，在当前页面弹出漏洞选择窗口；从智能分析发起时进入任务预案页再选择，不再切换到扫描发现；生成成功后后台建立任务草稿，页面不自动跳转。任务预案页同步显示生成进度和完整失败原因，重试时保留同一扫描任务上次提交的漏洞选择。用户仍可通过“前往任务预案”主动切换页面。

可执行预案生成时，按所选漏洞清单整理各项独立步骤，保持每项内部顺序和请求内容不变，再检查每项2至6步、正常对照、不同验证输入及请求范围。步骤缺失或多漏洞混用时，纠正请求携带实际漏洞编号及步骤要求；纠正后仍不合格则不保存可执行预案。该整理不会创建缺失请求，也不代表漏洞已经验证成功。

阶段栏区分尚未生成、草稿待提交和已提交待审批，不再将所有等待状态显示为“预案已就绪”。
