# PR #22 推荐偏置复查

日期：2026-10-11，时区 Asia/Shanghai。

## 结论修正

用户反馈“现在只推荐漏洞模板扫描（Nuclei）”。现场最新三份流水线的生成步骤均记录 `method=matched`、`playbook_id=vuln_template_nuclei`，反馈有事实依据。

原验收将测试、构建及接口一致性通过视为适合试部署，但没有充分验证“扫描 → 分析 → 预案选择”的业务合理性。推荐回归甚至直接要求配置发现将 Nuclei 排第一；测试通过证明了实现符合这条规则，不证明规则适合完整测试任务。当前不能认定 PR #22 已通过业务验收，也不建议按现状合并。

不是所有推荐候选都被删除：使用最新任务证据及现场预案库的只读快照，在本地内存数据库回放，每个任务仍返回 10 个候选。流水线只取最高分作为本任务推荐，导致主界面看到固定的 Nuclei。此问题发生在后端，重新打开客户端不能消除排序偏置。

## 根因

1. `playbookMatcher.js` 将安全头、Cookie 标志、phpinfo、目录索引等发现统一归为 `configuration`。Nuclei 的安全头或 exposure/config 参数得到固定基础分 16，含 Nikto 的方案得到 12；对这些不同发现只取同类最高信号，不能体现具体入口、多个不同能力需求或已完成扫描。
2. `pipelineEngine.js` 在 AI 生成未成功时调用匹配器，直接选 `ranked[0]`，只保存这一项，不保存完整候选及可选择的后续验证路线。因此配置类分数偏置被放大成“所有任务都推荐同一个方案”。现场步骤记录能确认走了匹配分支，但现存 journal 没有保存这几次 AI 生成失败的具体原因，不应猜测为模型、网络或参数问题。
3. 本次扫描实际主要发现配置问题；SQLi-Labs 的首页标题 `SQL Injections` 不是已证实的 SQL 注入证据。Nuclei 可以作为配置核验候选，但不能仅凭这些信息认定它是完整测试任务的唯一最佳预案，也不能为强行区分靶场而虚构 SQL 注入、上传或其他漏洞。

当前 DVWA 任务应用探测页标题为 `SYSTEM COMPROMISED`，没有高置信度 DVWA 指纹；这个事实可能与此前页面篡改有关，但本次没有调查页面来源、恢复靶场或补猜产品身份。不能把产品识别失败全部归因于 PR 的指纹限制。

## 额外发现

当前粗粒度基线 fallback 仍会根据普通 `web_vuln` 发现推荐 `HTTP Flood DoS Attack Simulation`：三个最新任务分别出现 7、9、9 分。扫描中没有对应的拒绝服务验证证据或任务目标，不能仅凭兼容 Web 类型和基线分类推荐这种影响型方案。这项预案只在候选列表中，本次未执行它。

这是推荐资格约束不足，不应通过把 Nuclei 的分数简单调低来解决；那样可能将不适合的后续方案顶到第一名。

## 后续修复方向

- 将“配置补充扫描”“侦察/入口发现”“漏洞定向验证”“影响型测试”明确区分，不把扫描类方案混作唯一攻击路线。
- 结合本任务已完成步骤、具体发现与可用入口进行能力匹配；同一任务内各扫描证据可聚合，但不能借用其他任务或过期记录。
- 在自动选择及审批界面保留候选、证据与待满足条件，证据不足时说明需要补充入口或探测，不能制造已验证漏洞。
- 影响型方案必须有明确任务目标与授权条件，不能只按通用基线命中。
- 增加真实流水线复现回归；测试业务约束，而不是固定要求某个工具始终第一。
