## 一、源主机脱离：来源采集的部署回归

两份云笔电拓扑均保留了 `task-origin` 节点，但 `ip` 为空、状态为 `unknown`，且没有关联边。节点备注明确说明任务未记录发起端地址。两条任务的服务器 `config` 均只有 `require_approval`，缺少 `topology_origin`。

部署前备份与当前服务器 `backend/src/routes/pipelines.js` 的差异显示：上一轮部署推荐优化时，整文件替换遗漏了以下既有逻辑：

1. 创建任务时，从真实 HTTP socket 采集源地址、服务端接收地址与时间。
2. 修改配置时，保留已有来源记录。
3. 启动任务时，再记录实际启动请求的来源。

这是本次助手部署造成的回归，不是云笔电真实断网，也不是拓扑渲染器将已知源主机错误移出网络。服务器拓扑构建器和云笔电拓扑页面仍保留原有 V2 实现；缺失的是上游任务来源。

本地定点修复恢复创建、配置更新和启动时的来源采集与保留；不接受客户端提供的来源字段，也不信任转发头替代真实 socket 地址。历史任务继续保留“来源未记录”，新建并启动的任务才应产生可信来源关系。

## 二、Pikachu 推荐预案失败：命令模板与调整渲染问题

### 第一步：Gobuster 没有指定 `dir` 子命令

`step1_gobuster_course_dict` 实际以 `-u` 开始，缺少目录枚举模式 `dir`。安装的 Gobuster 3.8.2 返回：

```text
flag provided but not defined: -u
```

该次尝试退出码为 `1`。旧模板另含 `-fw`，当前版本的 `dir` 也不支持此参数；仅补上 `dir` 仍不足以修复模板。第二步使用 `-s 403` 时，还应显式清空默认黑名单，避免白名单与默认黑名单冲突。

### 第二步：自动调整后，目标尚未替换便触发了阻断

ReAct 调整下一步时补上了 `dir`，但使用了 `http://target:8765`。执行准备先判定目标未解析，再进行目标归一化；即使归一化后的审计参数已指向本次目标，先前的准备错误仍然存在：

```text
Unresolved tokens: http://target:8765
```

该次尝试退出码为 `-2`，没有真正启动扫描工具。随后提出的追加步骤也被预案的 `disableAutoInsert` 约束阻止。该约束是安全边界，不应通过放开自动插入来掩盖模板问题。

本地修复范围：

- 两步模板均添加 `dir`、移除不支持的 `-fw`，403 白名单步骤添加 `-b` 和显式空字符串。
- 先将已知旧式目标占位符解析为当前执行目标，再做未解析变量校验；未知变量仍阻断，不改安全边界。
- 新增 `028_fix_recon_dir_enum.js` 迁移，仅更新预案库中与旧参数完全一致的 Gobuster 步骤；不覆盖自定义模板，不改已有执行记录。仅改 JSON 文件不足以更新已导入的预案库。

推荐该预案本身并不证明 Pikachu 不适合目录枚举。此次失败的直接证据是命令准备错误，而不是目标不可达。推荐规则后续还需要考虑模板的可执行条件与工具版本，不能只按匹配分判断可执行性。
