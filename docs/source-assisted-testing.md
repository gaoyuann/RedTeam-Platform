# C/C++ 源码扫描与现有 Playbook 流程集成

更新：2026-10-12。当前采用 **扫描云笔电集中扫描源码、靶场云笔电保持原部署**。若扫描云笔电使用原部署中的 112 地址，则对应关系为 112 扫描、113 靶场。旧的 [113 本机扫描设计](source-scan-113-local-design.md) 是未采用的备选方案，不是本次部署要求。

## 1. 目标与复用范围

核心流程沿用本项目已有能力：

```text
获取对应版本源码 → 冻结快照 → 静态工具扫描 → AI 结合代码分析
  → 扫描发现（文件/行号/证据/触发前提）
  → 现有扫描结果页面 → 生成并推荐验证 Playbook
  → 现有执行引擎 → HTTP/TCP 运行证据 → 人工复核
```

本次重点是把“源码漏洞发现”接入已有扫描、预案和执行记录体系，不新增独立的源码测试页面。任务工作台中创建 C/C++ 源码辅助测试后，扫描和分析完成即等待选择演示对象；不会自动套用 Web 库存预案。

### 1.1 演示要求与实际边界

| 要求 | 当前操作 / 记录 |
| --- | --- |
| 先扫描、对漏洞列表展示 | 同一工作台展示源码候选、位置、CWE、代码证据、前提和覆盖；候选不等同于运行时已确认漏洞 |
| 逐一演示扫描出的漏洞 | 单条发现可生成单项演示；多选清单按发现顺序生成独立的正常对照与验证步骤，每项 2–6 步，每份最多 10 项 |
| 确定目标与对象、选择若干漏洞并列表 | 选择弹窗展示固定运行目标、发现编号、名称、源码位置、前提与复核状态；生成成功后清单冻结在预案 metadata 中 |
| 根据清单演示攻击功能 | 复用任务预案审阅和执行验证；每一步和每条运行证据保留 finding_ids 与 baseline / verification 阶段 |
| 展示攻击结果 | 引用该发现对应的执行证据复核为“证据支持 / 未复现 / 条件不足”；工具成功、HTTP 200 和普通连通性不算攻击成立 |
| 所有被测源代码软件系统 | 需事先列出被测软件、部署入口、对应源码版本和源码目录，逐软件创建任务并核对覆盖；当前不会从一个 IP 自动发现所有已安装软件及其源码 |

复用的是任务、结果列表、预案和执行流程。C/C++ 缺陷使用源码证据与实际输入点生成专门的 HTTP/TCP 验证步骤，不把 SQL 注入等 Web 模板强行应用到任意代码告警。

可远程触达的输入校验或业务缺陷，可依据真实路由 / 文本协议做正常输入与验证输入对照。纯本地缺陷、无远程入口的越界 / UAF，以及需要进程崩溃、寄存器或堆栈证据的问题，当前请求验证器不能证明；预案应返回具体缺失条件。如果验收必须展示这类利用，需要另行提供靶场进程运行接口、调试 / sanitizer 证据收集与隔离重置能力，不能以静态告警替代攻击演示。

参考 pentagi-v3 的思路是保留分析细节、据此生成验证任务，再关联来源与验证结果。参考仓库的前端提交 Flow 给后端执行，并不能据此推断必须在被测主机安装源码扫描器。

| --- | --- | --- |
| vulnerable-webapp | http://192.168.1.113:8089/ | HTTP 验证 |

**网站地址是运行入口，不等于源码地址。** 要扫描源码，需要通过可下载的 HTTP 源码目录或 SSH 读取对应版本源码；普通网页响应通常不包含 C/C++ 实现。没有源码时，可以远程测试 HTTP/TCP，但覆盖记录明确为 remote_only，不产生“已扫描源码”的结论。

以上地址来自部署说明，本地开发测试没有访问或验证这些云笔电。

## 3. 源码如何进入扫描

源码可以放在靶场云笔电上，例如 `/home/user4/targets/vuln-demo`；扫描后端通过 SSH 固定只读脚本获取快照。平台本次不新增 Git 自动克隆或压缩包上传界面。

若源码已通过 Apache 目录索引提供，页面可直接填写源码目录 URL 或 `/` 开头的路径，并通过“浏览远端目录…”弹窗查看和选择。运行地址与源码目录分别保存；手动目录优先于后端项目映射。仅访问相同协议、主机和端口，不跟随重定向。目录浏览不是远端磁盘文件管理器，服务未提供索引时无法枚举文件。

将 data/source-scan/connections.example.json 复制为 data/source-scan/connections.json，按真实目录修改：

```json
[
  {
    "id": "vuln_demo_113",
    "name": "vuln-demo 对应版本源码（靶场云笔电）",
    "kind": "ssh",
    "host": "192.168.1.113",
    "port": 22,
    "username": "target-reader",
    "identity_file": "/etc/redteam/keys/target-readonly",
    "known_hosts_file": "/etc/redteam/ssh/known_hosts",
    "source_root": "/home/target-reader/targets/vuln-demo",
    "targets": ["http://192.168.1.113:8090/"],
    "architecture": "arm64"
  }
]
```

- `kind: ssh` 时，source_root 是 **靶场云笔电上的绝对目录**；密钥和 known_hosts_file 是扫描后端本机路径。如果改用 `kind: local`，source_root 才是扫描后端可读目录；如果后端在容器中，须使快照目录在后端容器内可见。
- targets 绑定具体程序入口，防止混用另一个程序的源码。绑定匹配包含路径；验证请求限制相同协议、主机、端口。
- architecture 描述被测程序架构，是分析上下文，不会使扫描器模拟 ARM64，也不证明编译参数正确。
- 可通过 SOURCE_SCAN_CONNECTIONS_FILE 指定配置文件。配置和快照已加入 .gitignore。
- 界面沿用现有扫描流程，接收靶场运行地址和可选 HTTP 源码目录；目录留空时按运行地址自动匹配项目。SSH、本机文件系统路径通过项目配置提供，页面不传递认证信息。项目列表不返回认证文件路径。

HTTP 目录索引是截图所示场景的优先方式；后端只读取选定根目录下的源码文件，目录名不固定为 `source`。若靶场不提供目录索引，SSH 来源仍可作为两台云笔电部署方式：只执行固定的只读收集脚本，不要求为靶场云笔电安装 cppcheck/Flawfinder。SSH 严格校验主机指纹；密钥或密码文件位于扫描后端；不通过页面传递密码。

## 4. 源码漏洞扫描的实现

### 4.1 收集和版本固定

sourceCollector.py 收集 C/C++ 文件；sourceSnapshot.js 将内容冻结到本次任务的只读快照。保存文件路径、内容哈希、读取时间、项目和架构，后续工具和 AI 使用同一版本。

当前限额：500 个文件、每文件 512 KiB、总内容 8 MiB，仅接受 UTF-8 文本。符号链接、二进制、超限及读取失败会记录。build、dist、vendor、node_modules、.git、.cache 等目录按规则排除，不属于本次扫描范围。

这能保证“报告对应哪份代码”，但不能证明靶场云笔电上的二进制由它构建。部署验收需要对照源码提交、发布记录及实际构建参数。

### 4.2 静态工具先产生候选位置

扫描云笔电上运行：

- **cppcheck**：发现其支持的越界、空指针、未初始化值等问题，以及部分可移植性和性能告警。
- **Flawfinder**：根据 C/C++ 危险函数及规则提示风险点，提供 CWE 等信息。

工具只读挂载本次快照到 /src/project，容器禁用网络。工具输出保留为扫描证据，告警定位必须对应快照内真实文件和行号。工具失败不会伪装为“未发现漏洞”。

静态工具告警是候选问题。危险函数调用可能受上游长度检查保护，不能仅凭函数名认定可利用。

当前没有接入项目的 compile_commands.json、完整宏配置和编译器数据流数据库，不保证覆盖所有条件编译分支。大项目应先按业务模块设置合理源码目录并核对覆盖情况；现有限额不适合声称完成整个 Apache 工程的全量深度审计。

### 4.3 AI 结合相关代码分析

默认每个主片段 120 行，20 行重叠；优先审查静态工具告警附近，默认最多 12 批。创建扫描 API 可设置 parameters.ai_batches 为 1–24；页面使用默认值。关闭 AI 后，静态扫描仍然可用。

每批输入包含：

1. 主片段及实际行号。
2. 对应静态工具告警。
3. 根据函数名出现位置和本地 include 检索的相关片段，最多 4 个、合计 16,000 字符。
4. 已取得的运行入口响应及被测架构信息。

AI 要分析输入来源、传播过程、危险操作、边界检查和触发前提，给出修复建议。证据链 trace 可引用 source、propagation、sink、guard、supporting 角色，保存实际代码和哈希。

后端校验：主发现必须在本批主片段；证据链只能引用本批实际提供的主片段或相关片段；每条引用最多 41 行。虚构文件、行号和未提供的片段都被拒绝并记录。

**相关代码检索是有界的词法检索，不是编译器证明的调用图。** 同名函数不代表真实可达，函数指针、宏和复杂跨文件调用可能遗漏。即使 ai_complete 为 true，也只表示所有已收集主片段完成了有效格式的审阅，不代表语义分析完整或所有漏洞都已找到。

### 4.4 合并告警并保留分析依据

同一文件、危险点起始行及 CWE（缺失时按标题）作为合并键：

- 保留稳定的扫描结果 ID。
- tools 记录检测来源；analyses 保存各次工具/AI 的依据、前提、建议和证据链。
- AI 补充说明不会因为已有静态告警而被丢弃。
- 合并后的严重性取最高值，AI 不会自动把工具告警标为“已排除”。
- CWE 或危险点不同的记录保留为独立发现，避免误合并。

标准发现包括 file、start_line、end_line、code、source_sha256、snapshot_id、cwe、reason、preconditions、suggestion、trace、tools、analyses。

所有静态发现保持 verification_status=needs_review、runtime_verified=false。

### 4.5 如实记录覆盖

source_coverage 保存读取文件数、跳过原因、静态工具状态、AI 批次数、已审阅主片段和关联片段的范围、无效引用及错误。

源码读取失败、模型不可用或预算不足时显示失败或部分完成；入口响应仍保留。ai_complete 不覆盖被排除或超限的文件。报告不能把未审阅代码算作安全。

## 5. 如何复用分析和 Playbook

| 原有模块 | 接入方式 |
| --- | --- |
| scan_tasks / scan_results | source_scan 保存源码发现、入口响应、覆盖及错误 |
| 扫描页面 | 同页查看代码、行号、相关证据链和不同检测来源 |
| 预案生成 | 给已有生成入口传入选中的 source_finding 和对应证据 |
| Playbook 列表 / 推荐 | 展示本次任务已生成的验证预案 |
| 执行引擎 | 按原有执行记录、步骤、取消及证据机制运行 |
| 复核 | 将具体发现关联至实际执行步骤和证据 ID |

源码任务暂不按 CWE 随意推荐通用端口扫描或固定 PoC：本任务的推荐列表使用基于本任务证据生成的预案。没有生成时列表为空；点击“选择源码发现 · 生成攻击演示清单…”或右键单项生成。未来复用库存验证模板时，还需明确其协议、输入点和前置条件，不能只靠 CWE 相同。

生成预案会包含来源发现、源码证据链、触发前提、具体请求和预期可观察证据。没有可信路由或条件不足时返回缺失信息。不能根据一个 strcpy 告警凭空编造 HTTP 参数。

单项远程诊断仍支持 1–6 步；逐项演示每个发现 2–6 步，最多 10 个发现 / 60 步，使用 target-request。后端校验发现顺序、独立关联、正常对照先于验证，以及验证输入不同于对照。等待条件与超时变化不算不同输入。预案编辑后的审批同样检查这些约束。

- HTTP 支持 GET、HEAD、POST、OPTIONS，不自动跟随重定向。
- TCP 支持同一连接内多轮文本交互，可等待实际菜单提示后再发送；每个步骤建立新连接，需要包含必要的前置交互。
- 单请求最长 30 秒；TCP 最多 10 轮、发送共 8 KiB；响应最多 64 KiB，超限保留部分证据并报告。
- 不提供 ARM64 调试、崩溃回收或任意二进制协议执行。

受限动态请求控制器可在单独扫描页选择；接口默认允许，generateSourceVerification 的内部默认 false。进入任务预案审批后的执行使用冻结步骤的 mechanical 模式，不动态追加请求，保证清单与演示步骤一致。

新任务 API 保留并校验 config.scan_mode=source_assisted、source_url 和 source_connection_id；源码地址按相同协议 / 主机 / 端口规范化。流水线把这些参数传给 source_scan，扫描分析后停在 source_selection，使用现有 awaiting_approval 状态。生成逐项预案并加载步骤后自动进入任务预案、建立草稿，沿用现有提审 / 批准 / 执行链路；重新进入任务可以从本任务来源预案列表恢复。任务草稿必须来自本任务扫描和同一目标的逐项演示预案；旧直接批准入口不能绕过清单。扫描启动后不能修改测试模式或源码来源。

执行状态 COMPLETED 只表示预案步骤完成。复核需要引用与该发现关联的步骤证据，填写“证据支持 / 未复现 / 条件不足”。连通性、HTTP 200 或一个菜单响应不等于内存漏洞已经验证。旧版本缺少逐步骤来源关联的运行记录需用新预案重新执行，才能作本次发现的复核依据。

报告现状：现有结果评估支持人工生成执行报告 / 任务追溯草稿；源码扫描结果和 source_verifications 人工复核尚未完整映射进报告正文。试测阶段可核对扫描页、执行证据和复核窗口，不能把当前导出的通用报告当成包含全部源码发现的最终报告。完整报告需继续接入源码版本、覆盖、发现位置、演示清单和逐发现复核。

## 6. 在扫描云笔电部署和使用

1. 保持项目原有后端运行方式；在扫描云笔电准备 Python 3 和兼容其 CPU 架构的 rt-sast-c 镜像。镜像构建与导出脚本已包含 sast-c；离线环境需导入该镜像。也支持既有 host 工具执行方式。
2. 把真实源码副本放在靶场云笔电，给扫描云笔电配置只读 SSH 和 connections.json。源码快照必须在扫描后端生成并可被工具容器正确挂载。
3. 后端启动运行 025_source_audits 迁移，新增版本和复核表；升级前按项目方式备份数据库。旧固定 source_code_poc_verify 模板已停用，原内容存放 docs/archive/source_code_poc_verify.json。
4. 在现有“新建测试任务”弹窗选择“C/C++ 源码辅助测试”，分别填写程序运行入口和可选源码目录；目录可用同一远端索引弹窗选择。创建并启动，保留现有模型配置。
5. 在“扫描发现”检查覆盖、阅读源码与前提，点击“生成攻击测试预案”或选择对象；生成成功后自动进入任务预案并建立草稿。重新进入任务可从本任务来源列表找回已生成预案。完整流程与环境清单见 [源程序测试链路与环境核对](source-workflow-and-environment.md)。
6. 沿用任务预案提审 / 批准流程执行；回到源码证据窗口引用该发现关联的实际执行证据复核。

单独扫描页仍可创建 C/C++ 程序测试、生成并前往执行。工作台源码任务没有候选或缺少验证入口时，保留扫描结果和缺失条件，不用远程诊断预案冒充漏洞演示。已有任务草稿不会被新生成的清单覆盖。

发现超过 10 条时需选择具体发现生成预案。程序任务重测应新建任务，保留版本和证据链。旧版以目录名作 target 的任务可查历史，但必须新建真实运行地址任务才能生成预案。

快照存放 data/source-scan/snapshots，当前不自动清理。运维按留存要求清理不再引用的快照，避免影响正在扫描或复核的任务。

## 7. 验证、效果评估及合并条件

本地检查：

```sh
cd backend
npm run test:source
SOURCE_TEST_SAST=1 npm run test:source
npm run test:topology
npm run test:topology:pipeline
cd ..
cmake --build build -j2
```

源码测试涵盖真实静态工具、快照、HTTP/TCP、取消、超时、源文件引用校验、跨文件证据、告警合并、预案执行和人工证据关联。AI 回复通过测试替身提供，不能把测试通过等同于真实模型的漏洞发现效果。

部署后先在每个程序建立“已知漏洞 + 修复后的安全版本”对照集，记录：
