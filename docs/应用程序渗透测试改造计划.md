# 改造计划：从"靶场演示工具"到"应用程序渗透测试平台"

> 日期：2026-08-30
> 目标：将平台从依赖预设靶场（DVWA/Windows AD）的演示工具，改造为面向任意应用程序的智能化渗透测试平台

---

## Context

当前平台 70%+ 的 playbook 为预设靶场（DVWA 19个、Windows AD 11个）硬编码，平台本质上是靶场的"遥控器"。老师要求的是**应用程序**——一个独立安装即可用的渗透测试软件，用户指向任意目标，平台智能扫描分析并自动编排攻击。

核心矛盾：**已知靶场 → 已知漏洞 → 硬编码脚本** vs **未知应用 → 未知架构 → 需要智能决策**

改造核心：用 AI + 扫描驱动工作流弥合"已知"与"未知"之间的鸿沟，把靶场从"核心依赖"降级为"可选演示"。

---

|-------|------|------|--------|------|--------|

## Block 1：Playbook 通用化（⭐⭐，2-3天）

### 目标
将 playbook 从"靶场答案"改造为"通用方法论"，去掉 DVWA 专属路径硬编码，让 playbook 能对任意 Web 应用生效。

### 问题分析
- `dvwa_file_tamper.json` 中硬编码了 `/login.php`、`/vulnerabilities/upload/`、`/hackable/uploads/` 等 DVWA 专属路径
- `genericWebTargetAdapter.js` 仍然输出 `dvwa_login_url`、`sqli_url` 等 DVWA 变量
- 19 个 `target_class: dvwa` 的 playbook 在非 DVWA 目标上全部被 preflightGate 拦截
- `scanExecutor.js` 的 `brute_force` 模式默认尝试 `/login.php`

### 改造步骤

#### 1.1 清理 genericWebTargetAdapter 的 DVWA 污染
**文件**: `backend/src/services/targetAdapters/genericWebTargetAdapter.js`

- 移除 `dvwa_login_url`、`sqli_url`、`dvwa_sqli_url`、`dvwa_cookie` 等字段
- 这些字段只应在 `dvwaTargetAdapter.js` 中出现
- 添加通用应用层变量：
  ```js
  api_base_url: `${scheme}://${host}:${port}/api`,  // 常见 API 前缀
  login_url: `${base_url}/login`,                     // 通用登录路径
  admin_url: `${base_url}/admin`,                     // 通用管理路径
  ```

#### 1.2 改造 DVWA 专属 playbook 为通用版
**文件**: `data/playbooks/dvwa_file_tamper.json` 及其他 DVWA playbook

策略：**保留原 DVWA playbook 不动**（教学用途），创建对应的通用版本：

| 原 playbook | 通用版 | 改造要点 |
|---|---|---|
| `dvwa_file_tamper` | `web_file_upload_exploit` | 去掉 `/vulnerabilities/upload/` 硬编码，改为扫描发现上传点 |
| `sqli_to_shell` | `web_sqli_to_rce` | 去掉 DVWA SQLi 路径，改为从扫描结果注入 |
| `demo_web_full_killchain` | `web_auto_killchain` | 去掉 DVWA 登录流程，改为通用 Web 杀伤链 |
| `golden_dvwa_max_tools` | 保留（纯教学） | 不改造 |

通用 playbook 的关键变化：
- `target_class` 从 `dvwa` 改为 `web_url`
- `targetType` 从 `["dvwa"]` 改为 `["web_url", "local_ip"]`
- `args_template` 中的硬编码路径改为 `{{base_url}}` + 通用路径
- `disableAutoInsert` 改为 `false`（允许 ReAct 根据发现动态插入步骤）

#### 1.3 scanExecutor 去掉 DVWA 默认假设
**文件**: `backend/src/services/scanExecutor.js`

- `brute_force` 模式中，当 `service === 'http-post-form'` 且无 `form_definition` 时：
  - 当前：默认尝试 `/login.php`（DVWA 假设）
  - 改为：不追加路径，让工具自行探测；或使用通用路径列表 `['/login', '/signin', '/auth/login', '/api/login']`

#### 1.4 playbookMatcher 增强通用匹配
**文件**: `backend/src/services/playbookMatcher.js`

- 当前 `PORT_CLASS_GROUP_MAP` 只有 6 条规则，增加通用 Web 应用匹配：
  ```js
  '80:web_url': 'web-vuln-scan',
  '8080:web_url': 'web-vuln-scan',
  '443:web_url': 'web-vuln-scan',
  '8443:web_url': 'web-vuln-scan',
  ```
- 对 `target_class === 'web_url'` 的目标，降低 DVWA-only playbook 的推荐权重（已有部分实现，增强）

### 验证方式
1. 创建一个指向任意 Web URL（如 `http://httpbin.org`）的扫描任务
2. 扫描完成后查看 recommendations，应推荐通用 playbook 而非 DVWA playbook
3. 选择通用 playbook 执行，preflight 应通过（不被 target_class 拦截）
4. 执行步骤中不应出现 DVWA 专属路径

## Block 3：扫描→分析→生成 串联（⭐⭐⭐，5-7天）

### 目标
实现老师要求的"先扫描 → 展示结果 → 智能生成 Playbook → 再执行"工作流。当前扫描和生成是分离的手动步骤，需要串联为自动化流水线。

### 问题分析
- `scans.js` 已有 `/:scanTaskId/recommendations` 和 `/:scanTaskId/generate-playbook` 端点
- `playbookGenerator.js` 已能从扫描结果生成 playbook
- 但整个流程需要用户手动点 4-5 次按钮跨越 3 个页面
- 没有统一的流水线状态跟踪

### 改造步骤

#### 3.1 创建统一流水线数据模型
**新建文件**: `backend/src/db/migrations/013_add_pipeline_tables.js`

```sql
CREATE TABLE IF NOT EXISTS pipelines (
  pipeline_id   TEXT PRIMARY KEY,
  target        TEXT NOT NULL,
  status        TEXT DEFAULT 'created',  -- created→scanning→analyzing→generating→ready→executing→completed→failed
  scan_task_id  TEXT,
  analysis_result TEXT,        -- LLM 分析结果 JSON
  generated_playbook_id TEXT,  -- AI 生成的 playbook
  run_id        TEXT,          -- 执行 run
  config        TEXT DEFAULT '{}',  -- 流水线配置（scan_types, auto_execute 等）
  result        TEXT,          -- 最终结果摘要
  created_by    TEXT,
  created_at    TEXT,
  updated_at    TEXT
);

CREATE TABLE IF NOT EXISTS pipeline_steps (
  pipeline_id   TEXT NOT NULL,
  step_order    INTEGER NOT NULL,
  step_type     TEXT NOT NULL,  -- scan, analyze, generate, execute
  status        TEXT DEFAULT 'pending',
  input_data    TEXT,
  output_data   TEXT,
  started_at    TEXT,
  completed_at  TEXT,
  error_message TEXT,
  PRIMARY KEY (pipeline_id, step_order)
);
```

#### 3.2 流水线引擎
**新建文件**: `backend/src/services/pipelineEngine.js`

核心流程：
```
用户输入 target
    ↓
[Step 1: scan]  并行执行多类型扫描
  - port_scan (nmap)
  - web_scan (nikto + nuclei)  ← 如果是 Web 目标
  - vuln_scan (nuclei)
    ↓
[Step 2: analyze]  LLM 分析扫描结果
  - 识别技术栈（Spring Boot? Django? Express?）
  - 发现攻击面（开放端口、Web 路径、API 端点）
  - 评估风险等级
  - 输出结构化分析报告
    ↓
[Step 3: generate]  LLM 生成针对性 playbook
  - 基于分析结果选择攻击策略
  - 生成 playbook（复用 playbookGenerator.js）
  - 或匹配现有 playbook（复用 playbookMatcher.js）
    ↓
[Step 4: execute]  执行 playbook
  - 创建 execution_run
  - 启动执行（ReAct 模式）
  - 实时推送进度
    ↓
[Step 5: report]  生成评估报告
```

关键实现：
```js
export async function runPipeline(pipelineId) {
  // Step 1: Scan
  await runPipelineScan(pipelineId);
  // Step 2: Analyze (LLM)
  await runPipelineAnalysis(pipelineId);
  // Step 3: Generate Playbook
  await runPipelineGeneration(pipelineId);
  // Step 4: Execute (if auto_execute)
  if (config.auto_execute) {
    await runPipelineExecution(pipelineId);
  }
}
```

#### 3.3 增强扫描分析（Step 2）
**新建文件**: `backend/src/services/scanAnalyzer.js`

当前 `playbookGenerator.js` 直接把扫描结果喂给 LLM 生成 playbook，缺少"分析"环节。新增分析层：

```js
export async function analyzeScanResults(scanTaskId) {
  // 1. 获取扫描结果
  const results = getScanResults(scanTaskId);

  // 2. LLM 分析
  const prompt = `分析以下扫描结果，输出结构化报告：
  - 技术栈识别（语言、框架、中间件、数据库）
  - 攻击面清单（端口、路径、API、认证方式）
  - 风险评估（按 OWASP Top 10 分类）
  - 推荐攻击策略（优先级排序）

  扫描结果：
  ${JSON.stringify(results)}

  输出 JSON 格式...`;

  const analysis = await callLlm([{ role: 'user', content: prompt }]);

  // 3. 存储分析结果
  saveAnalysis(scanTaskId, analysis);

  return analysis;
}
```

分析结果格式：
```json
{
  "tech_stack": ["Spring Boot 2.7", "MySQL", "Nginx"],
  "attack_surface": [
    { "type": "open_port", "port": 8080, "service": "http", "detail": "Spring Boot Actuator" },
    { "type": "web_path", "path": "/actuator/health", "risk": "info_leak" },
    { "type": "web_path", "path": "/api/users", "risk": "idor" }
  ],
  "risk_assessment": [
    { "category": "A01:2021-Broken Access Control", "confidence": 0.8, "evidence": "..." },
    { "category": "A05:2021-Security Misconfiguration", "confidence": 0.9, "evidence": "Actuator exposed" }
  ],
  "recommended_strategy": [
    { "priority": 1, "action": "Test Actuator endpoints for info leak", "tools": ["curl", "nuclei"] },
    { "priority": 2, "action": "Fuzz API endpoints for IDOR", "tools": ["ffuf", "arjun"] }
  ]
}
```

## Block 4：目标分类与适配器扩展（⭐⭐⭐，3-5天）

### 目标
扩展目标分类系统，支持应用程序级别的目标（REST API、GraphQL、移动端 API 等），让平台能识别和适配不同类型的应用。

### 改造步骤

#### 4.1 扩展 target_class
**文件**: `backend/src/services/targetProfileResolver.js`

新增目标类别：

| 新 target_class | 识别规则 | 说明 |
|---|---|---|
| `web_app` | URL 含 `/api/`、`/graphql`、`/v1/`、`/v2/` 等路径 | Web 应用（非纯静态站） |
| `rest_api` | URL 路径匹配 `/api/v\d+/`，或 whatweb 检测到 `Swagger`/`OpenAPI` | REST API 服务 |
| `graphql_api` | URL 路径含 `/graphql` 或 `/gql` | GraphQL 端点 |
| `spa_app` | whatweb 检测到 `React`/`Vue`/`Angular` | 单页应用前端 |

识别逻辑增强——两阶段分类：
1. **静态分类**（当前）：基于 URL 模式和 IP 规则
2. **动态分类**（新增）：扫描后基于 whatweb/nmap 结果修正

```js
export function refineTargetProfile(initialProfile, scanResults) {
  // 如果扫描发现 Swagger UI → 升级为 rest_api
  // 如果扫描发现 /graphql → 升级为 graphql_api
  // 如果扫描发现 React/Vue → 标记为 spa_app
  // 返回修正后的 profile
}
```

## Block 5：执行→反馈→调整 闭环（⭐⭐⭐⭐，7-10天）

### 目标
增强 ReAct 引擎的适应性，使其能对未知应用程序做出更智能的决策。当前 ReAct 主要服务于已知靶场场景（"按计划推进"），需要改造为面向未知目标的"探索-验证-利用"循环。

### 问题分析
- 当前 ReAct prompt 强调"Playbook 锚定"——严格推进现有 playbook
- 对未知应用，应该更鼓励"探索"——根据证据动态调整策略
- 当前 `buildInsertHint` 只有一个启发式规则（HTTP 端口 → 插入 gobuster）
- 失败处理只有"adjust 重试"和"continue 跳过"，缺少"换一种攻击方式"

### 改造步骤

#### 5.1 双模式 ReAct Prompt
**文件**: `backend/src/services/reactEngine.js`

新增"探索模式"prompt，与当前"锚定模式"并存：

```js
// 锚定模式（当前）：严格推进 playbook，适合已知靶场
// 探索模式（新增）：鼓励基于证据探索，适合未知应用

function buildReactPrompt({ ..., explorationMode }) {
  if (explorationMode) {
    return buildExplorationPrompt(...);
  }
  return buildAnchoredPrompt(...);  // 当前的 prompt
}
```

探索模式 prompt 核心原则：
1. **证据优先**：每一步都基于前一步的真实输出决策
2. **鼓励探索**：发现新攻击面时优先 insert 新步骤，而非 continue
3. **快速失败**：某条攻击路径 2 次失败就换方向
4. **广度优先**：先枚举所有攻击面，再深度利用
5. **禁止盲猜**：不利用 LLM 先验知识假设目标特征

#### 5.2 增强启发式规则库
**文件**: `backend/src/services/reactEngine.js`

当前 `buildInsertHint` 只有 1 条规则。扩展为规则库：

```js
const INSERT_RULES = [
  // 规则 1：HTTP 端口 → 目录枚举（当前）
  { condition: 'hasHttpPort && !hasDirEnum', action: 'insert', tool: 'gobuster', ... },

  // 规则 2：发现 API 路径 → 参数发现
  { condition: 'hasApiPath && !hasParamDiscovery', action: 'insert', tool: 'arjun', ... },

  // 规则 3：发现登录页面 → 认证测试
  { condition: 'hasLoginForm && !hasAuthTest', action: 'insert', tool: 'hydra', ... },

  // 规则 4：发现 SQL 错误 → SQL 注入测试
  { condition: 'hasSqlError && !hasSqliTest', action: 'insert', tool: 'sqlmap', ... },

  // 规则 5：发现 Actuator 端点 → 信息泄露测试
  { condition: 'hasActuator && !hasActuatorTest', action: 'insert', tool: 'curl', args: ['{{base_url}}/actuator/env'], ... },

  // 规则 6：发现 JWT → JWT 攻击测试
  { condition: 'hasJwtToken && !hasJwtTest', action: 'insert', tool: 'jwt_tool', ... },
];
```

#### 5.3 流水线驱动的 ReAct 初始化
**文件**: `backend/src/services/executionEngine.js`

当执行由流水线触发时，将扫描分析结果注入 ReAct 初始上下文：

```js
// 在 executeRun 中，如果 run 来自 pipeline
if (run.plan_data) {
  const planData = JSON.parse(run.plan_data);
  if (planData.pipelineAnalysis) {
    // 将分析结果注入 ReAct 的初始 evidenceHistory
    evidenceHistory.push({
      stepIndex: -1,  // 虚拟步骤，表示流水线分析
      toolId: 'pipeline_analyzer',
      success: true,
      output: JSON.stringify(planData.pipelineAnalysis).slice(0, 500),
    });
  }
}
```

这样 ReAct 从第一步就有扫描分析的上下文，而不是"盲打"。

#### 5.4 增强失败恢复策略
**文件**: `backend/src/services/reactEngine.js`

当前失败处理：adjust 重试 / continue 跳过 / stop 终止

新增策略：
- **pivot**：当前攻击路径失败，切换到完全不同的攻击向量
  - 例：SQL 注入失败 → pivot 到目录枚举寻找其他入口
- **escalate**：当前工具能力不足，请求更强力的工具
  - 例：gobuster 没发现有用路径 → escalate 到 ffuf 用更大字典

```js
case 'pivot':
  // LLM 指定新的攻击方向
  if (decision.toolId && decision.args) {
    // 清除当前方向的后续步骤
    // 插入新方向的步骤
  }
  break;
```

#### 5.5 证据驱动的动态目标修正
**文件**: `backend/src/services/executionEngine.js`

当 ReAct 发现新的子目标时（如扫描发现内网 IP），自动扩展目标列表：

```js
// 在 ReAct insert 处理中
if (decision.action === 'insert' && decision.newTarget) {
  // 记录发现的子目标
  db.prepare('INSERT INTO discovered_targets (run_id, target, source_step, discovered_at) VALUES (?, ?, ?, ?)')
    .run(runId, decision.newTarget, step.step_index, new Date().toISOString());
}
```

### 验证方式
1. 对未知 Web 应用执行 playbook，ReAct 应在"探索模式"下运行
2. nmap 发现 8080 端口 → ReAct 应自动 insert whatweb/gobuster 步骤
3. 发现 SQL 错误 → ReAct 应自动 insert sqlmap 步骤
4. sqlmap 失败 → ReAct 应 pivot 到其他攻击向量而非 stop
5. 流水线触发的执行，ReAct 第一步应有扫描分析上下文

## Block 6：前端工作流一体化（⭐⭐⭐⭐，5-7天）

### 目标
将 ScanPage → PlaybookPage → ExecutionPage 的割裂流程，改造为统一的"扫描→分析→生成→执行"一站式工作流。

### 问题分析
- 当前 3 个页面几乎不共享上下文（ScanPage 不传递 target 给 ExecutionPage）
- AI 生成 Playbook 期间无进度反馈（60s 阻塞等待）
- ExecutionPage 用 HTTP 轮询而非 WebSocket 推送
- 没有全局工作流状态指示器

### 改造步骤

#### 6.1 新增 PipelinePage
