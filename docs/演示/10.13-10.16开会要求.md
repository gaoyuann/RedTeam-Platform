#### 4.3.1 靶场扫描覆盖要求（10 月 16 日讨论补充）

以下为会议后项目讨论补充，不追溯为原会议结论，也不代表功能已经实现。本轮优先完成靶场的完整流程，暂不处理源程序的全流程。

“全面扫描”应以明确范围内的覆盖清单验收，不能仅以启动了多少个工具、返回了多少条记录判断完成；也不承诺自动发现所有真实漏洞。

| 检查层次 | 覆盖要求 | 验收依据 |
| --- | --- | --- |
| 资产覆盖 | 明确授权范围内的主机、服务和应用；记录已发现、不可达及尚未检查的对象。 | 对照靶场资产清单，说明差异与探测位置；未知资产总数时不计算资产发现率。 |
| 应用入口覆盖 | 对 Web/API 识别路径、接口、参数、表单和认证入口；对非 Web 服务记录协议、端口及适用的交互入口。 | 保存已发现入口、登录状态、角色和未覆盖原因；缺少认证条件时明确标注。 |
| 检测能力覆盖 | 根据实际服务与入口安排适用检查；列出未支持、不适用及需要人工补充的检查。 | 提供“资产／入口—检查项—执行状态”清单；私有 IP 不直接等同于 Web 应用。 |
| 执行覆盖 | 区分完成、失败、超时、中止和跳过；保留原因及已有结果。 | 每个计划检查项有最终状态；执行失败或未检查不能解释为未发现漏洞。 |
| 结果完整性 | 核对工具输出、解析、入库、接口和页面各环节；全部发现可查询，合并后仍可追溯原始记录。 | 对账各环节数量与差异；记录未解析、过滤和合并的原因，防止静默丢失。 |

展示和统计补充要求：

1. 扫描进行时展示进度及阶段状态；扫描结束后集中呈现完整结果。技术详情按需展开，失败或中止时也应能查看已获得的结果。
2. 漏洞、资产信息、信息级发现、工具错误分别展示；开放端口和技术指纹不直接计入漏洞数。AI 摘要不能替代完整结果列表。
3. 同一漏洞的多工具证据可以合并，但需保留来源；不同资产、入口或位置的漏洞实例不能随意合并。
4. “应有漏洞数”以明确版本、配置的靶场已知漏洞清单为依据；基准未知时标注未知，不虚构发现率。
5. 第一项整改工作为核对选定靶场的扫描覆盖并打通全部发现的统一展示，随后接通载荷匹配、逐漏洞验证、统计及环境恢复。

## 5. 源码漏洞扫描分工与问题

### 5.1 本次会议确定的协作方式

1. 浪涛将其基于 PentAGI 的源码扫描功能单独提炼为一个服务。
2. 本项目调用该服务进行源码漏洞扫描。
3. 扫描完成后，本项目后续流程仍使用自己的 HexStrike；浪涛的后续流程继续使用其 PentAGI。

### 5.2 当前问题与待核实事项

1. 会议记录认为目前本项目的源码扫描尚不能满足要求，主要问题是无法确定扫描对象是否覆盖完整源码；该判断需结合实际扫描范围和结果核实。
2. 需要明确源码输入范围、完整性确认方式及扫描覆盖情况，解决“不知道扫的是不是完整源码”的问题。
3. 原记录指出 Nmap 不能承担源码漏洞扫描，需要专门的源码分析方式。
4. 本项目此前的思路是使用 C/C++ 代码扫描工具，结合 AI 分析，按“先静态、再动态”的方式开展测试。该思路作为背景保留，与新扫描服务的衔接方式待明确。
