## 1. 协作入口与使用方式

本文用于查找任务、理解边界和安排交接；**对应 GitHub Issue 是负责人、当前状态、确认后的日期、Plan、PR 和验收证据的统一记录入口**。表中编号和范围是导航，不表示当前进度；认领前先打开 Issue 核对，避免重复开发。

1. 选择任务，在 Issue 中说明认领意向，确认未被他人认领后登记唯一主责（Assignee 或正文负责人）。
2. 阅读实现、调用方、测试及已有改动，提交执行 Plan，等待项目负责人确认。
3. 实施前与相邻任务负责人约定接口及共用文件；在独立分支和工作目录开发。
4. 通过相关检查后关联 PR，补充使用说明、证据及限制，请另一人验收。
5. 单项验收通过后关闭 Issue；跨模块演示由 F12 负责人统筹。

职责或范围变化时更新本文和相关 Issue；日常状态、人员、日期和证据仅在 Issue 维护，避免两份记录不一致。会议原要求、后续设计方向与待决策事项按各自确认程度落实，历史“已实现”描述不能替代验收。

## 2. 分工原则与推进顺序

按功能交付分工：主责覆盖该项涉及的前端、后端、数据、测试与说明。现场同学协助设备、网络或环境操作，不改变功能主责。每人一次推进一个主要功能，先核验已有能力，再补齐缺口。

| 阶段 | 任务与目标 | 并行方式 |
| --- | --- | --- |
| 第一批 P0 | F04：已有扫描结果的保存、任务汇总和完整展示 | 一人推进 F04；另一人盘点 F01 环境与 F11 设备条件 |
| 第二批 P1 | F02、F03：任务范围、资产服务发现及适用检查计划 | 复用 F04 的结果契约，先落实选定靶场的最小检查清单 |
| 后续闭环 P2 | F05—F10：拓扑、载荷、逐漏洞验证、统计和恢复 | 接口确定后可分别开发；已有载荷路径先验证，再接新载荷路径 |
| 联合验收 | F12：完整演示与 2—3 轮复测 | 提前安排环境时段，由整体验收协调人跟踪跨模块问题 |
| 同步文档 | D01—D03：需求、设计初稿与演示说明 | 从功能分析阶段开始整理，不等待开发结束 |

F04 不等待 F03 的新扫描编排，可用现有任务和隔离样例开发；先约定父子任务归属、范围和权限。相关鉴权或归属缺陷纳入 F04 的 Plan，不扩展为完整 F02 改造。真实靶场验收依赖 F01。

现场条件较多的 F01、F10、F11、F12 优先由便于现场操作的人认领；扫描结果、载荷和统计等可由远程协作者承担。以实际能力、可用环境和 Issue 认领为准，不固定某人负责整层代码。F08—F10 也应明确主责，不默认全部交给扫描负责人。

P0/P1/P2 表示实施顺序，不表示 P2 可推迟到演示之后。接口样例可以用于开发和隔离测试，真实链路验收必须单独完成并记录。

## 4. 开工确认与进度记录

### 4.1 执行 Plan 必须说明什么

| 内容 | 要求 |
| --- | --- |
| 问题与证据 | 当前行为、触发条件、影响；区分已复现问题、代码风险和待验证项 |
| 修改范围 | 拟修改文件、前后端行为、数据/API/权限变化，以及本次不处理的内容 |
| 协作影响 | 关联 Issue、接口契约、共用文件、旧数据及调用方兼容 |
| 验证与交付 | 具体检查命令、前提、验收标准、证据、未运行检查及原因 |
| 风险与安排 | 回退方式、阻塞、建议日期及需要项目负责人决定的事项 |

Plan 获明确确认后实施，并在 Issue 中记录确认内容和版本。确认前仅做范围内只读分析及经核对无外部副作用的现有隔离测试；实质性范围变化需更新 Plan 后再确认。认领、建议日期或 Issue 创建都不等于实施授权。

### 4.2 状态与记录模板

统一状态：`待认领 → 分析中 → Plan 待确认 → 开发中 → 待联调 → 待验收 → 已完成`。存在阻塞时记录阻塞点、所需协助及下一步；Q 类使用 `待确认`，并记录最终决策。

可将以下内容放入 Issue 正文，进展或交接时更新：

```text

目标日期（待确认或已确认）：

接口交接及依赖：
验证结果 / 证据链接：
阻塞 / 未解决限制 / 下一步：
验收人 / 验收结论：
```

## 5. 职责边界与接口交接

交接时至少提供字段含义、稳定标识、状态、错误、权限约束及一份脱敏样例，并在关联 Issue 中记录双方约定。

| 提供方 → 使用方 | 交接内容 |
| --- | --- |
| F01 → F02/F03/F08/F09/F10 | 环境版本、执行位置、范围、资产与已知漏洞基准、认证引用及恢复条件；未知项明确标注 |
| F02 → F03/F08 | 父任务与运行标识、范围/排除项、所有者权限、预算及配置版本 |
| F03 → F04/F05/F09 | 资产、服务、入口及来源；检查项标识、计划、适用性和执行状态 |
| F04 → F06/F08/F09 | 稳定原始发现 ID、父子任务及运行归属、位置、来源和证据；合并实例另给 ID 与映射 |
| F06/F07 → F08 | 载荷 ID、版本、类型、消费方式、变量及可用状态；F08 回传实际使用及验证结果 |
| F04/F08 → F05 | 关联资产/服务的发现、扫描及验证状态与证据；回填必须对应当前运行 |
| F08 → F09 | 发现或漏洞实例引用、Playbook/载荷版本、验证结论、判定证据及尝试记录 |
| F04/F08 → F10 | 扫描和验证活动调用、取消结果、实际停止状态或隔离依据，不能只提供界面状态 |
| 各功能 → F12、D01—D03 | 功能版本、验收证据、说明及限制；F12 协调跨模块复验，文档负责人组织材料 |

以下边界在联调前必须明确：

- **跨端调用**：F01 负责环境和集成验收协调；F04 负责现有扫描调用的数据及错误返回，F03 负责新增检查适配，F08 负责验证适配。网络可达不能替代工具调用验收。
- **发现与拓扑**：F03 主责资产、服务和入口发现；F05 主责拓扑构建、展示及交互。私有 IP 不直接等同 Web 应用，实测连接也需区分路由、可达或归属语义。
- **记录与漏洞实例**：F04 先提供稳定原始发现引用；F09 主责统一去重和统计，与 F04 约定实例映射。未可靠去重时明确标注记录数，不改写原始证据。
- **载荷与验证**：F06/F07 提供可用载荷；F08 证明具体步骤实际消费了哪一版本。验证也允许无需独立载荷或工具内部生成输入；无 Playbook 时按确认方案补充或标记待补条件。
- **统计与恢复**：工具成功不等于漏洞成立；未知基准不计算发现率。F10 必须同时确认扫描和验证停止或影响已隔离，恢复失败不能标记环境可复用，删除环境不算恢复。

## 6. 开发、联调与验收规则

### 6.1 避免代码和环境冲突

1. 各用独立分支和工作目录，不共用运行数据库或构建目录。开工前检查已有改动，不覆盖他人工作。
2. 共用文件提前约定修改人和顺序，尤其是扫描/执行编排、任务结果、API 客户端、主窗口、路由装配、构建清单及数据库迁移；迁移编号先登记。可由一人代接公共入口，不为分工大规模重构。
3. 合入前同步已完成修改并解决冲突；接口变更通知使用方，不能用整文件覆盖解决冲突。
4. 共用靶场预约扫描、验证、部署与恢复时段；禁止一人测试时另一人恢复。远端操作前阅读[异机配置手册](../Codex异机配置手册.md)，重新核验环境状态。
5. 实际扫描、攻击、远端写入、服务重启、运行数据库迁移及恢复须有具体任务范围和授权。仅发布必要脱敏证据；通用说明放 `docs/`，本机诊断放 `.codex/`，不写入秘密。

### 6.2 第一批 F04 的最低验收标准

目标：一次靶场扫描结束后，能完整看到本次全部发现，并清楚知道哪些检查没有完成。本批不开展工具扩容、按服务动态编排、拓扑重构、载荷生成或自主攻击改造。

| 验收项 | 必须满足 |
| --- | --- |
| 全量查询 | 超过 150 条扫描候选仍可查全；分页稳定，总数及筛选范围一致；AI 摘要不能代替完整列表 |
| 任务级汇总 | 覆盖本次运行全部子扫描，保留来源，校验归属权限；不混入其他任务或旧运行 |
| 稳定引用 | 换页、排序、刷新和新增记录不改变同一发现的身份；原始发现与合并实例分别标识 |
| 结果对账 | 工具报告、解析、入库、API、页面的差异可解释；未解析、过滤、合并及截断不静默处理，未知总数不虚构 |
| 类型与计数 | 工具候选、资产、信息、AI 候选及错误可区分；无载荷发现仍显示；AI 重述不重复计为漏洞；未去重时标明记录数 |
| 异常与取消 | 非零退出、超时和中止保留可用部分发现；错误文本不当漏洞；取消后不再派发，晚到回调不改为成功 |
| 重试与兼容 | 覆盖重复回调、重试、重新执行、旧格式、空结果、部分失败及异步刷新；清空旧数据的现有行为先分析，再在 Plan 中确定修复 |
| 证据 | 提供隔离测试、数量对账、列表及异常截图；未完成授权靶场实测时标记待验收 |

超出 150 条属于边界验收场景，不代表当前代码仍有同样限制。具体缺陷与修复状态以 F04 的分析、PR 和验证记录为准。

### 6.3 每项任务完成的条件

- 按批准范围交付可用功能，关联 PR、版本及必要数据兼容说明。
- 后端按 `backend/package.json` 运行相关 `npm test`；Qt 沿用既有 CMake 配置验证构建和交互。检查权限、异常、取消、重复执行及旧数据，记录失败和未运行检查的原因。
- 提供简短使用说明、脱敏证据与未解决限制；需要现场条件却未验证的，保留待联调或待验收状态。
- 由另一位协作者复核验收，结果写入 Issue；单项通过不能替代 F12 的完整演示。
- 文档交付保留版本及审阅结论；同一个 Word/PPT 或 UML 图源文件同一时间由一人编辑，其他人提供章节或意见。
