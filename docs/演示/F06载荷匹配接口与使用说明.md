# F06 载荷匹配接口与使用说明

## 使用动线

任务扫描结果页选择“全部子扫描”后，漏洞候选行的“匹配载荷”列显示“候选”“已关联”“需重新确认”或“暂无匹配”。双击该行或使用右键菜单可查看匹配依据、前置条件、待核对条件、载荷类型、消费方式和版本指纹，并将所选载荷关联到该条原始发现。没有匹配载荷时，漏洞行仍显示。

此处的关联是验证计划的输入。它不会发起攻击，也不表示漏洞已证实或载荷已实际被使用。F08 需要在 Playbook 步骤中引用载荷，并回传实际消费的版本和执行证据。

## 数据与匹配规则

- 以 `scan_results.id` 标识原始发现，关联表 `finding_payload_links` 保存发现 ID、载荷 ID、版本指纹、匹配依据、消费方式、操作者和历史版本。新增迁移 `032_finding_payload_links.js` 只增加表与索引，不改写旧扫描记录或载荷数据。
- 静态载荷与 `generated_payloads.import_status = 'accepted'` 的载荷可供匹配；待审核或已拒绝的生成载荷不可关联。版本指纹由载荷内容计算，内容变化后旧关联显示“需重新确认”，重新关联会保留旧版本历史。
- 优先匹配明确的 CVE 标识；没有精确标识时只将明确的漏洞类型与载荷主类别对应。产品不一致的载荷会排除；产品、入口、变体或前置条件无法从发现中核实的条目仅作为“待核对”候选。信息级发现、工具错误和否定性结果不会产生漏洞载荷匹配。
- 旧载荷常包含整段命令或教学步骤，当前消费方式为 `playbook_step_reference` 或 `tool_command_reference`。执行器不得将它们直接当成请求参数或已执行的证明。变量字段缺失时返回空对象。
- 任务结果仍是原始记录，`payload_match` 只是该行的展示摘要；一个发现可以有多个关联。F04 若提供合并后的漏洞实例 ID，仍需保留原始发现 ID 与实例 ID 的映射。

## API

以下接口均要求有效登录身份，并限于任务创建者或管理员；修改关联沿用 `/api/pipelines` 的写权限。

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/pipelines/:id/results?view=scans&category=vulnerability` | 分页返回完整原始发现；漏洞行新增 `payload_match` 摘要，状态为 `candidate`、`linked`、`stale` 或 `none`。 |
| `GET /api/pipelines/:id/results/records/:recordId/payload-matches` | 返回该发现的 `finding_id`、`matches` 和历史 `links`；候选包括 `payload_id`、`version`、`payload_type`、`consumption`、`variables`、`prerequisites`、`missing_conditions`、`match_basis`、`availability` 和 `match_status`。 |
| `POST /api/pipelines/:id/results/records/:recordId/payload-links` | 请求体 `{ "payload_id": "sqli-mysql-basic", "version": "sha256:…" }`；验证发现归属、载荷可用性、匹配依据和版本后保存关联，重复提交同版本幂等。 |

无效编号或非漏洞关联返回 400；跨任务发现返回 404；非本任务所有者返回 403；载荷已变化返回 409，客户端应重新读取匹配结果。旧库若尚未运行迁移，结果读取仍可显示候选；写入关联前须按部署流程迁移数据库。

## 已知边界

现有静态载荷多数只有类别、标签和自然语言前置条件，缺少机器可判定的产品版本范围。因此类别匹配始终是待核对候选，不能表示适用条件全部满足。当前 UI 展示原始漏洞候选列表，尚无 F04 的去重实例映射，也未接通 F07 的缺失载荷生成和 F08 的逐漏洞执行消费。
