## 2. 安全与复现原则

1. **只使用隔离测试。** 新增的回归测试必须使用假工具运行器、临时目录、内存/测试数据库和 `.invalid` 示例域名；不得在本计划实施中发起真实扫描、爆破或利用。
2. **目标必须可追溯。** 每次调试记录原始目标、规范化目标、允许范围和最终实际调用目标；日志中仅保存脱敏后的目标与凭据标识。
3. **先复现、后修复。** 每个缺陷都必须先有失败用例，再做最小修复，最后留下稳定回归测试。
4. **区分代码与环境。** 缺字典、容器工具版本差异、部署版本落后、服务重启等问题不能伪装成代码修复完成。
5. **不破坏当前批次成果。** 不重置工作区、不覆盖未提交改动；每个调试批次单独记录变更、验证命令和结论。

## 4. P0-1：目标与模板门禁

### 4.1 建立单一规范目标

1. 在运行或流水线创建时仅生成一次 `canonicalTarget`，来源为 `normalizeTarget` 的结构化结果。
2. 将该对象作为执行上下文传递给模板渲染、工具参数规范化和结果记录；后续步骤不得自行重新拼接协议、主机、端口或路径。
3. 每次边界转换后校验：协议仅出现一次、主机非空、端口合法、未保留 `target`/`example`/`CHANGE_ME` 等占位符。
4. 发现重定向、扫描发现或适配器返回的新地址时，先做授权范围校验；它不能无条件覆盖初始规范目标。
5. 不要粗暴禁止 `127.0.0.1`：仅当初始授权目标本身就是回环测试目标时允许保留；其他目标在执行中被改写为回环地址必须拒绝并记录原因。

### 4.2 必须新增的失败用例

| 输入场景 | 期望结果 |
| --- | --- |
| `http://http://fixture.invalid` | `PREPARATION_ERROR`，工具运行器调用次数为 0。 |
| `http://target:8765/install.php` 或 `{{target}}` 未解析 | `UNRESOLVED_TEMPLATE`，记录变量名/模板位置，工具运行器调用次数为 0。 |
| 已授权的 `https://fixture.invalid` 被步骤改写为 `127.0.0.1` | `TARGET_SCOPE_VIOLATION`，保留原规范目标和拒绝原因。 |
| 初始授权目标就是测试回环地址 | 在假工具运行器中允许执行，证明校验不会误伤合法隔离测试。 |

## 5. P0-2：工具参数、字典与运行镜像契约

### 5.1 工具命令在启动前完成结构化校验

在 `backend/src/tools/toolContracts.js` 或其相邻的专用契约层中，为每种受影响工具建立可测试的输入规则，而不是依赖工具的自然语言报错：

| 工具/能力 | 调试检查 | 期望处置 |
| --- | --- | --- |
| Nmap | 同时出现 `-F` 与 `-p`；URL 未转换为主机/端口。 | 返回 `INVALID_TOOL_ARGUMENTS`，不启动 Nmap。 |
| Gobuster | 缺少 `dir` 子命令、`-u`、`-w` 或版本不兼容参数。 | 规范化为受支持命令，无法规范化则预检失败。 |
| Hydra | 主机、服务/端口、用户名/密码字典、HTTPS 服务模式不完整。 | 返回可读的契约错误；字典检查先于进程启动。 |
| 字典资源 | 文件缺失、为空、不可读，尤其是日志中引用的 `rockyou.txt`。 | 返回 `RESOURCE_MISSING`，包含逻辑资源名与部署提示，不泄露敏感路径。 |
| 系统工具 | `grep -P` 等依赖 GNU 特性的命令在 BusyBox 镜像中不可用。 | 采用可移植实现，或在镜像能力预检时明确拒绝。 |

### 5.2 字典资源的部署决策

日志显示当前工作区并不具备引用的 `rockyou.txt`。实施时必须二选一并记录部署约束：

1. 在受控镜像/部署包中提供经过授权的字典，并用资源清单校验其可读性与版本；或
2. 修改 Playbook，明确使用仓库已有且许可合规的较小字典。

不得因为“让任务跑通”而静默替换字典；这会改变任务覆盖范围和结果含义。

## 6. P0-3：业务结果、步骤状态与流水线错误

### 6.1 统一执行结果结构

工具运行器、执行引擎和流水线之间统一传递以下字段：

```text
code                 机器可读错误码，例如 SEMANTIC_TOOL_FAILURE
stage                preparation | execution | classification | pipeline
runId / stepIndex    可定位到运行与步骤
toolId               产生结果的工具
canonicalTarget      脱敏后的规范目标
exitCode             原始进程退出码（可为空）
failureReason        非空、面向用户的摘要
stderrSummary        脱敏且截断的诊断信息
retryable            是否可重试
```

### 6.2 语义失败分类规则

1. 继续保留退出码判断，但不能仅以退出码为成功条件。
2. 将 `FATAL`、`VERIFY_FAILED`、`FILE_TAMPER_FAILED` 等业务失败信号按**工具/步骤上下文**分类为失败，避免在普通输出中做过宽的全局字符串匹配。
3. 区分三种状态：`COMPLETED`、`PARTIAL`、`FAILED`；发现信息但验证步骤失败时，不得显示为完整成功。
4. `executionState` 聚合失败步骤时必须保证 `failureReason` 非空；`pipelineEngine` 写入流水线记录时应优先使用该字段，禁止产生 `undefined` 作为最终错误消息。
5. 每个失败状态都应保留底层运行 ID、步骤序号、工具 ID 和脱敏后的 stderr 摘要，方便从流水线反查。

### 6.3 必须新增的失败用例

| 假工具返回值 | 期望执行状态 | 期望流水线记录 |
| --- | --- | --- |
| `exitCode: 0`，输出含受上下文约束的 `FATAL` | `FAILED` | 有非空 `failureReason`，可定位步骤。 |
| `exitCode: 0`，验证步骤输出 `VERIFY_FAILED` | `FAILED` | 不得标记为完整成功。 |
| `exitCode: 0`，篡改验证输出 `FILE_TAMPER_FAILED` | `FAILED` | 流水线错误不得为 `undefined`。 |
| 单步骤失败且其他步骤完成 | `PARTIAL` 或 `FAILED`（依 Playbook 策略） | 总状态、步骤状态和错误摘要一致。 |

## 7. P1：ReAct、动作白名单与类别限额

1. 为 LLM 输出定义严格动作枚举及参数 schema；解析失败、未知动作和缺失参数都生成 `INVALID_REACT_ACTION`。
2. 取消未知动作自动 `continue` 的静默回退。默认策略应是“停止并等待人工确认”或“明确失败”，由产品策略决定并写入配置。
3. 将类别限额的拒绝原因写入运行事件：已执行数量、上限、请求动作、是否有替代动作。
4. 将“发现有效信息但未完成验证”记录为 `PARTIAL`，避免自动策略把它等同于成功或失败后继续无限尝试。
5. 对未知动作、限额拒绝、空模型输出各增加确定性单测；测试不得调用真实模型服务。

## 8. P2：服务重启、连接恢复与状态对账

1. 客户端将连接拒绝视为暂时性传输错误，采用指数退避和抖动重连；重连期间保持最后一次已确认的运行状态并明确展示“正在恢复连接”。
2. WebSocket 不可用时，自动回退到受限频率的 HTTP 状态轮询；当前环境缺少 Qt WebSockets 时，该降级路径是必测项。
3. 后端启动后应对未完成运行进行状态对账：读取持久化的运行/步骤状态，不能仅依赖内存事件。
4. 使用受控的假连接失败与假重启场景验证，不在调试过程中重启生产服务。

## 10. 每批实施与验证流程

### 批次开始

1. 记录当前提交标识、`git status --short` 摘要、部署版本/镜像标识和涉及的运行 ID。
2. 只读核对失败日志所对应的部署版本是否包含当前仓库的修复；若不一致，先标记为“历史部署问题”，不可直接据此修改现代码。
3. 为本批次选定一个 P0/P1/P2 工作包，先提交失败测试，再做最小修复。

### 批次结束

1. 运行本批新增的定向测试。
2. 运行后端完整单测：

   ```bash
   JWT_SECRET=debugplan-isolated-fixture npm --prefix backend test
   ```

3. 保持前端上下文回归：

   ```bash
   cmake -S . -B build -DBUILD_UI_CHECKS=ON
   cmake --build build -j2
   ctest --test-dir build -R 'ui-context-' --output-on-failure
   ```

4. 检查补丁格式：

   ```bash
   git diff --check
   ```

5. 在调试记录中写明：失败用例、根因、修改文件、验证结果、未解决风险及是否需要部署侧变更。

## 12. P0 验收门槛

P0 全部完成前，不将失败日志中的执行问题标记为解决。验收必须同时满足：

- 目标重复协议、未解析占位符和未授权目标漂移均在工具启动前被拒绝。
- Nmap、Gobuster、Hydra 的已知错误输入和缺失字典均得到结构化预检错误。
- `FATAL`、`VERIFY_FAILED`、`FILE_TAMPER_FAILED` 的模拟结果不会因退出码为 0 被误判成功。
- 流水线错误消息始终非空，能反查到失败步骤；不再出现 `undefined`。
- 新增定向测试、既有 34 项后端测试、三项 UI 上下文 CTest 和 `git diff --check` 均通过。
- 若运行环境仍缺少字典、工具能力或 WebSocket，记录为部署前置条件或已验证的降级行为，而非隐藏为代码成功。
