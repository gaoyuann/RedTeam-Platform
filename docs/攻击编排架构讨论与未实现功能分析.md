## 一、攻击测试3类编排架构讨论

### 1.1 当前实现的问题

现在3类编排本质上就是**一个下拉过滤条件**——按 `baseline_group` 筛选 playbook 列表。这在功能上等于"搜索过滤"，不构成一个独立的功能点。如果需规把它列为"漏洞攻击测试"下的3个子功能，那当前实现显然没有达到应有的层次。

### 1.2 从实际攻击流程看三者的关系

三类攻击在真实红队行动中**不是并列的三个独立动作，而是有逻辑递进关系的**：

```
① 数据抵近窃取 ──→ ② 信息篡改欺骗 ──→ ③ 关键设备夺控
   (探查窃取)          (篡改欺骗)          (持久控制)
```

- **窃取是前提**：你得先拿到数据/凭据，才知道篡改什么、控制什么
- **篡改是手段**：拿到数据后，篡改 DNS/会话/日志来掩盖行踪或误导防御方
- **夺控是目标**：最终要的是对关键设备的持久控制权

但这个递进**不是刚性的**。实际场景中：
- 有时先拿到一台设备的 shell（夺控），再从这台机器往外窃取数据
- 有时篡改和窃取是交替进行的
- 有时只做其中一类就够了

**结论：三者有逻辑关联、有典型顺序，但不应该硬编码为固定流水线。**

### 1.3 应该提升到什么层面

引入**攻击战役（Campaign）**概念，把3类编排从"playbook标签"提升为"战役阶段"：

```
当前（太浅）：
  ExecutionPage → 3个RadioButton → 过滤playbook列表 → 选一个执行

应该（提升后）：
  CampaignPage → 创建战役 → 3个阶段面板 → 每阶段内编排多个playbook → 阶段间可串联/跳过
```

具体提升点：

| 层面 | 当前 | 应该 |
|------|------|------|
| 数据模型 | playbook 上的一个字段 `baseline_group` | 独立的 `campaigns` 表 + `campaign_phases` 表 |
| UI | 3个 RadioButton 过滤列表 | 3个阶段面板，各有状态/进度/结果摘要 |
| 执行 | 选一个 playbook 跑 | 阶段内可编排多个 playbook，阶段间有推进逻辑 |
| 结果 | 只看单次 run 的 evidence | 阶段级汇总 + 战役级汇总报告 |

### 1.4 阶段间关系：松耦合、有引导

- **推荐顺序**：默认按 窃取→篡改→夺控 推进，UI 上有视觉引导
- **阶段前置条件**：比如"信息篡改"阶段可以标注"建议先完成数据窃取阶段"，但不强制
- **结果传递**：阶段1的产出（窃取到的凭据/IP列表）可以作为阶段2/3的输入
- **允许跳过/重排**：用户可以直接从夺控开始，或者只做其中一两类

### 1.5 阶段内部编排能力

当前是"选一个 playbook 执行"，但一个阶段通常需要多个 playbook 配合：

```
数据抵近窃取阶段：
  ├── ICMP隐蔽信道探测 (侦察用)
  ├── HTTP隧道外泄      (主攻击)  
  └── 凭据哈希破解      (为后续阶段准备凭据)
```

阶段内 playbook 之间也应该有执行顺序（串行/并行/条件分支）。

## 三、优先级排序

### P0 — 必须实现

1. **Campaign攻击战役模型** — 3类编排从过滤标签提升为一等公民
2. **口令加密存储** — 当前明文存储是严重安全缺陷
3. **并发扫描调度** — 至少支持多任务并行

### P1 — 应该实现

1. **多AI代理架构** — 3-5个核心代理
2. **资产探测功能** — 基于nmap/masscan主动资产发现
3. **态势感知模块** — 安全态势仪表盘
4. **后门探测** — rootkit/webshell扫描
5. **网络数据捕获** — tcpdump/tshark流量捕获
6. **LLM专用配置区域** — 独立UI

### P2 — 可以实现

1. **靶场部署管理** — VulnHub/CTFd
2. **VS Code扩展** — 轻量级第二前端
3. **银河麒麟适配** — Qt5已兼容，需实测
4. **漏洞库数据** — NVD/CNNVD集成
