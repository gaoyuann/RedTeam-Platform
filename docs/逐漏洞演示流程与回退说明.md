# 逐漏洞演示流程与回退说明

整改范围按会议确认的五项：加密狗、拓扑扫描、逐漏洞攻击效果、载荷生成与复用、统计结论。本次连接扫描后的主流程，保留原有任务流程；不将局部功能测试当作完整现场演示通过。

## 流程选择与兼容

创建任务时，“测试方式”默认是“逐漏洞攻击演示（推荐）”，可以选择“整任务预案（原流程）”。客户端记住此次选择，用于下次新建任务；任务本身保存独立选择，其他客户端使用自己的新建任务默认值。

| 配置 | 行为 |
| --- | --- |
| `config.workflow=per_finding` | 扫描后展示漏洞表，按所选漏洞准备方案、载荷并确认执行，最后主动汇总 |
| `config.workflow=legacy` | 保留原来的整任务流程 |
| 未提供 `workflow` 的历史任务或调用 | 按原流程读取和运行，不自动转换 |

任务启动后禁止修改流程；不能用切换流程绕过正在执行的调用、停止确认或审批。

原普通任务流程：扫描 → AI 分析 → 整任务预案生成 → 审批 → 执行 → 结果。
原程序/源码任务流程：扫描与分析 → 选择发现 → 生成程序预案 → 草稿与审批 → 执行。

## 新流程的实际操作

1. 创建任务，选择目标类型和“逐漏洞攻击演示”。快速测试创建后开始扫描，完整配置创建后在任务中点击启动。
2. Web 填写目标 URL；程序选择运行入口；源码选择源码目录并填写对应程序的运行入口。只有源码时可以扫描，但不能拿源码目录服务冒充被测程序进行动态验证。
3. 扫描过程中显示状态与已保存结果。扫描后直接进入漏洞表，默认筛选漏洞候选，显示对应载荷、测试状态与结论。资产、信息和工具错误可切换筛选查看。
4. 双击一条或勾选多条打开演示窗口。先选择方案，需要时明确触发 AI 生成/调整。载荷先查库、再生成；预览后手动选择步骤绑定。无需独立载荷的检查不强行生成载荷。
5. 核对目标、前提、输入和判据后确认测试；批量按顺序执行。打开窗口、选择方案和保存草稿不自动攻击。
6. 查看本次尝试的实际响应、关键证据、自动判断及人工复核。关闭窗口或轮询刷新后，漏洞表与统计显示最新结果。
7. 点击“结束本轮演示并汇总”。未测试和待复核项如实保留；有活动扫描、验证或停止未确认时拒绝结束。结束后可查看、复核历史，新的测试应新建任务。

没有有效发现时展示空列表、错误和覆盖说明，不自动调用普通分析模型生成风险事实或整任务攻击方案。所有扫描均失败时任务保留失败状态。

## 统计口径

- 候选、已提交、实际测试按当前任务的稳定 `scan_results.id` 分别计数，尚未跨工具去重，不能宣传为独立漏洞实例数。
- 实际测试要求本次执行证据标记工具确实启动。预检失败或工具尚未启动只算提交/尝试，不算实际测试。
- 多次尝试不增加已测试条目；执行失败与漏洞结论分别统计。最新尝试的人工复核优先于自动判断。
- “应有漏洞”目前显示未知；本轮未接入靶场已知漏洞基线，不计算没有分母依据的检出率。
- 汇总不代表所有漏洞已测试或目标安全。受支持的自动判断目前为响应头、Cookie 属性、目录索引；其他攻击效果仍需对应方案和真实证据复核。

## 三条现场验收路径

分别新建 Web、源码及程序运行入口任务，不能仅从历史记录开始。各自保留目标版本、任务编号、扫描证据、方案与载荷版本、执行尝试和复核结论。

每条路径核对：可达目标与不可达目标；有效候选与空结果；已有载荷、生成失败和成功后复用；单条与顺序执行；取消及停止未确认；汇总与重新打开。源码与运行版本需匹配，源码发现本身不证明动态效果。

现场至少有一项已知真实效果的攻击及其对照，不能只用防护响应头检查代替全部攻击演示。真实模型、靶场、ARM64、加密狗拔插及拓扑迁移仍须单独验收。

## 回退

### 提交与合并边界

逐漏洞主流程及其统计、载荷展示共用接口和状态字段，应作为完整功能提交审查，不单独摘取界面文件。相关代码、回归测试和两份流程说明纳入提交；本地密钥说明、整改参考原文、运行数据库、环境配置及构建输出不纳入此次提交。

合并前核对功能提交的文件清单和测试结果，保留合并前主分支提交编号。合并不代表现场真实靶场验收完成；演示对象为 DVWA、Pikachu、SQLi-Labs 与被测软件，不扩大为仓库中所有可用靶场镜像。

### 撤销方式

对普通功能提交使用 `git revert <功能提交编号>` 创建撤销提交；若采用 squash 合并，撤销主分支上的 squash 提交。若使用 merge commit 并要撤销整个 PR，应先核对主分支对应的父提交，再用 `git revert -m 1 <合并提交编号>`。这些命令是回退时执行的操作，不要在仍有活动调用时直接运行或部署。

在干净的回退分支上进行撤销，检查后重新构建、运行旧流程回归，再更新客户端和后端。撤销源码不会自动替换运行中的二进制，也不会撤销已发生的目标请求。本功能没有新增数据库迁移，但新流程的任务与执行记录仍需保留；先结束或核实停止，不能假定旧代码可继续处理新任务。后续代码若依赖本功能，应先检查依赖和冲突。

优先使用业务回退：新建任务选择“整任务预案（原流程）”，之后的新任务走原流程。已有任务继续使用其保存的流程，扫描、载荷、执行证据和人工复核不删除、不覆盖。

本次不新增数据库表或迁移。若还需整体撤回代码，应先盘点活动调用和整改任务，确认其结束或已停止，核对数据库及客户端备份，再审核本次实际提交并生成反向提交。保留数据不等于旧代码能继续执行新流程中的任务，不能在活动任务上直接降级。不要执行强制重置、清库或删除运行数据。
