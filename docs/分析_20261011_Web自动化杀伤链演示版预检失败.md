## 修复决策：演示版与通用版不合并

此前的临时讨论曾考虑把演示版改成通用 Web 流程；核对源码、数据库和目标后，该方向已否定。两套预案职责不同，应继续独立存在：

- `demo_web_full_killchain` 保留为 **DVWA 专用演示版**。它包含带 CSRF 会话处理的登录验证，因此不能接受仅能证明“是 Web 服务”的 Pikachu 或其他产品。
- `web_auto_killchain`（Web 自动杀伤链·通用版）保持不变，继续接受 `web_url` / `local_ip`，不依赖 DVWA 登录页或固定产品路径；另一套 `web_vuln_exploit` 也不在本次修改范围。

本次修复内容：

1. 演示版 `targetType` 收紧为 `dvwa`，Pikachu 等泛 Web 目标会在预检的目标兼容性检查中失败，而不是进入错误的 DVWA 步骤。
2. DVWA 目标识别增加同源 `/login.php` 兜底探测。即使首页被靶场篡改为 `SYSTEM COMPROMISED`，只要登录页仍有 DVWA 指纹，预检仍能正确识别；不会跨域探测。
3. 将不存在的 Nuclei ID 替换为已核验存在的 `http-missing-security-headers`、`dvwa-default-login`、`phpinfo-files`、`phpmyadmin-panel`。
4. 将 Gobuster 旧式 `-m dir` 改为 3.8.2 支持的 `dir` 子命令；保留运行时兼容归一化。
5. 将末步从固定、无 CSRF 处理的 Hydra 表单改为容器内置 `web-brute`，使用目标登录页自动获取 CSRF 令牌与 Cookie；仍保留教师复核属性。
6. 新增 `027_sync_demo_web_killchain.js`，完整同步演示版的 playbook 行和步骤行，避免只改 JSON 而服务器数据库继续使用旧契约。

离线验证已通过：后端全量测试 `109/109`；4 个 Nuclei ID 均在本地模板库存在；使用真实 DVWA 地址进行的只读预检演练通过 13 项检查。补充兼容旧扫描入口传入脚本路径的调用方式。尚未执行登录口令验证或完整攻击链，等待用户在部署后测试。

## 3. 模板修正后仍会遇到的执行问题

### 3.1 Gobuster 使用了当前版本不支持的参数

线上第三步参数开头为 `-m dir`。实际镜像中的 Gobuster 为 3.8.2，需要使用 `dir` 子命令。

在禁网、只读、删除全部 capability 的临时容器中，仅执行帮助模式：

```text
gobuster -m dir --help
Incorrect Usage: flag provided but not defined: -m
```

生产代码只读编译与参数规范化后，`-m dir` 原样保留。编译器却将该步骤标为 `READY`，说明现有编译检查没有识别这个 CLI 契约错误。

### 3.2 Hydra 别名导致端口参数没有被移到正确位置

线上第五步使用 `http-form-post`。实际 Hydra 9.5 接受这个别名，并将其解释为 `http-post-form`；因此不能简单把失败归因于“模块名不存在”。

但是，`toolContracts.js` 用于定位 Hydra 目标位置的匹配列表包含 `http-post-form`，没有包含 `http-form-post`。URL 目标转换为主机后，新补的 `-s 8765` 被保留在服务及表单参数后面：

```text
... 192.168.1.111 http-form-post <表单参数> -s 8765
```

实际镜像为 Alpine 3.19.9 / musl。禁网帮助模式对比表明参数顺序会改变解析结果：

- 使用 `-U` 帮助模式且把端口放在末尾，输出 `Help for module 192.168.1.111`。
- 同样的参数，仅将 `-s 8765` 移到目标主机之前，输出正确的 `Help for module http-post-form`。

这验证了参数解析隐患；没有进行密码尝试或向靶场发起认证请求。修复应统一别名并保证 Hydra 选项在位置参数之前，而不是只修改预案里的字符串。

### 3.3 通用 Web 预案实际写死了 DVWA 登录表单

预案声明支持 `web_url` 和 `dvwa`，最后一步却固定为：

```text
/login.php:username=^USER^&password=^PASS^&Login=Login:F=Login failed
```

排查时进行两次普通 GET 请求：

| 请求路径 | HTTP 状态 | 页面标题 |
| --- | --- | --- |
| `http://192.168.1.111:8765/` | 200 | `Get the pikachu` |
| `http://192.168.1.111:8765/login.php` | 404 | `404 Not Found` |

目标是 Pikachu，而不是 DVWA。即使模板和命令参数都修好，也不能用 DVWA 的固定登录表单对这个 404 地址完成有效认证测试。

因此需要把通用 Web 检测与产品专用认证验证分开：没有确认产品、真实登录入口和认证契约时，不应执行固定 DVWA 登录步骤。

## 4. 哪些不是本次根因

- 不存在模板目录整体缺失或本次后端账户无法读取模板库的问题。
- 本次只读编译成功，5 个步骤均为 `READY`，载荷引用都能够解析；不是 Payloader 载荷库整体没有安装。
- 目标端口没有从 Nmap 参数中完全丢失：生产规范化后为 `-p 80,8765`。仍保留额外的 80 端口，但不能说这次只探测了 80；本次没有实际运行 Nmap。
- 线上审计记录 318 显示，在批准环节预案由 `vuln_template_nuclei` 改为 `demo_web_full_killchain`。这证明发生了预案覆盖，但不能仅凭审计判断是用户主动选择还是前端默认选择。
- 当前演示预案的失败与 DVWA `4280` 首页被篡改导致的产品识别失败不同，不能混为同一个故障。
