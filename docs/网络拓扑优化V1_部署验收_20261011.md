## 本版模型

- 上方为“测试设备逻辑交换机”，按本次任务的源主机、扫描执行端、目标及观测路径角色动态分组。
- 下方为“其他发现主机逻辑交换机”，收纳同一发现范围内、未被本次任务证据标记为测试成员的响应主机；不是按已知 IP 名单分类。
- 两个交换机是同一局域网的展示分组，不代表发现了两个实体交换机、两个 VLAN 或跨网通信，不补造交换机间连线或虚拟路由器。分组没有成员时不生成空交换机。
- 局域网范围来自扫描执行环境的接口、掩码及直连路由；邻居只做存活发现，不扩展到邻居的漏洞扫描或攻击。
- 任务请求边、路由观测边与逻辑归属边保留不同语义，响应路径不等于物理布线。
- 主机标签不再被 IP 默认显示名称遮住；没有主机名证据时显示 IP。厂商信息不是设备用途或主机名称。
- 移除通过 HTTP/SSH 等服务 Banner 的 Debian、Ubuntu 等字样推断宿主机操作系统的逻辑；服务版本信息仍保留。

## 部署过程与采集回归

暂停等待其他部署后，恢复时发现服务器的 `scanExecutor.js` 已被替换为缺失拓扑采集功能的版本：流水线仍传入 `discover_topology: true`，执行器却没有 `--iflist`、traceroute、LAN 发现及结构化主机归属解析。最新日志因此只有服务和 Web 扫描结果，无法从中生成完整拓扑。

在服务器当前代码快照上定点合并上述采集逻辑，保留另一部署增加的非阻塞警告、WhatWeb 处理及执行契约修复。替换前校验文件哈希，保留备份；确认没有活跃工具进程后重启后端。数据库中的旧 RUNNING 记录未被修改。之后的新扫描已产生 `network_context`、`lan_scope` 和 `lan_host_discovery`。

## 识别边界及后续反馈

- 已实际发现 `113`，但 LAN 存活响应本身不能证明其用途为“源代码靶场”，也不能证明它与服务器存在独立物理直连。当前将其归为其他发现主机，未硬编码用途。
- 如需要其他靶场也归入上方测试组，应根据可靠资产配置、登记信息或进一步角色识别证据分类，不能按 `.111/.112/.113` 地址后缀判断。
- 未取得 LLDP、交换机 MAC/端口表等证据时，本版仍是有观测依据的逻辑拓扑，不是完整物理交换机布线图。
- 旧任务不会借用新任务的来源或 LAN 结果补图；没有采集证据时应显示未知或提示重新探测。
- 云笔电构建提示已有 ARM64 ROCKEY SDK 缺失问题，属于与拓扑无关的运行功能限制，本轮未处理。
