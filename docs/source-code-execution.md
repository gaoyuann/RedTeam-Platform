# 源码发现、载荷与本地验证执行

源码扫描仍由 CScan 完成。逐漏洞窗口现在支持两条明确的验证路径：

- **实际目标 HTTP 验证**：设置授权范围内的运行入口和部署版本，准备正常对照与验证请求，使用已有 `target-request` 执行；结果只对应指定响应差异。
- **本地模拟验证**：从已保存的漏洞证据生成 Python/C/C++ 程序，准备绑定该程序的方案，确认后在独立容器编译、运行两组输入；结果只对应模拟程序的输出差异。

本地模拟不要求实际目标运行入口，也不证明真实部署程序存在同一漏洞。它不会编译、部署用户整个项目。需要额外软件包、网络、浏览器或长期服务的程序不属于当前本地执行环境。

## 操作与数据关联

1. 从源码发现打开逐漏洞测试，进入“载荷代码”。
2. 点击“生成载荷”或“生成本地验证程序”。生成只调用既有模型并保存记录，不执行代码。
3. 选择生成的文件，点击“准备本地载荷测试”。后端读取同一验证项下的生成记录，并保存完整文件、执行说明、载荷编号与哈希。准备不再请求模型改写代码，也不访问目标。
4. 点击“开始测试”。确认窗口展示本地执行范围、入口、两组输入、预期特征和载荷哈希。
5. 在“测试结果与历史”查看实际编译、运行输出、退出状态及证据。一个尝试内每阶段各运行一次，重复请求编号不重放。

生成结果新增 `execution`：

```json
{
  "language": "python",
  "entrypoint": "repro.py",
  "baseline": {"args": ["normal"], "stdin": ""},
  "probe": {"args": ["probe"], "stdin": ""},
  "expected_output": "具体的验证运行独有特征",
  "diagnostics": "none"
}
```

支持 `python`、`c`、`cpp`，入口扩展名为 `.py`、`.c`、`.cpp`；同一生成记录最多四个文件，可包含 `.h`/`.hpp`。C/C++ 以同语言源文件共同编译，不接收模型提供的编译参数。两阶段独立运行，不能依赖前一阶段留下的文件。

新生成记录默认明确保存 `diagnostics: none`，用于普通逻辑输出对照；验证依赖 ASan/UBSan 时必须声明 `asan_ubsan`。需要诊断库但当前工具链无法编译时直接停止，不取消诊断参数后重新运行。旧记录没有该字段时保留原来的 C/C++ 诊断要求及内容哈希，不能默默降低历史方案的验证条件。

`POST /api/pipelines/:id/verifications/:verificationId/code-plan` 接收 `expected_revision` 和 `artifact_id`。载荷只能引用当前验证项下的 `ready` 记录，源码发现指纹须与生成时一致。方案保存在现有 `finding_verification_plans.content.code_payload`，包含冻结文件和 SHA256；执行调用参数只含载荷编号、哈希和阶段，不接受内联代码或宿主机路径。

原有 `finding_verification_code` 历史继续可读。旧记录没有结构化执行说明或来源指纹时，不猜测入口和参数，页面提供重新生成入口。准备新版本不会重置每漏洞三次尝试的上限。源码发现、载荷、任务范围变化会阻止旧方案启动；历史执行证据继续保留。

## 执行环境与部署

复用后端实际选中的 Docker 或 Podman 引擎中的现有工具镜像，不新增镜像，不要求为执行脚本重建镜像：

| 载荷语言 | 复用镜像 | 所需能力 |
| --- | --- | --- |
| Python | `rt-web` | Python 标准库 |
| C | `rt-sast-c` | Python、GCC 和标准 C 开发库 |
| C++ | `rt-sast-c` | Python、G++ 和标准 C++ 开发库，按实际镜像检查 |

仓库的 `rt-web` 定义已安装 Python，`rt-sast-c` 定义已安装 Python、GCC、musl 开发库，但未声明 G++ 或诊断库，因此不能承诺所有 C++/ASan 验证均可执行。运行时发现缺少编译器会保存明确的失败依据，不运行验证程序，不安装软件包、不换镜像。诊断库或依赖缺失则保留编译错误，不转成验证成功或未复现。

固定监督脚本位于 `backend/src/tools/sourceCodeWorker.py`，随后端源文件部署。后端以单独的参数将脚本传给镜像中的 `python3 -I -B -c`，冻结载荷通过标准输入传入；不经 shell，不依赖镜像内预装监督脚本。容器无宿主机目录挂载、无网络、只读根文件系统、非 root 用户、无 capabilities；只允许有限临时目录、CPU、内存、进程数和文件大小。编译最长25秒，单次运行10秒，每阶段后端等待最长60秒，计划总时限120秒。输出每通道保留最多32 KiB，超限或超时不作肯定或否定判断。

缺少引擎或镜像时明确预检失败，不能退回宿主机执行生成代码。取消或超时会终止并移除命名容器，再通过容器列表确认其不存在；不能确认停止时保留 `unknown` 并阻止重试。执行不需要 CScan 在线，也不会创建新的 PentAGI Flow。

本次新增迁移 `038_source_payload_queue.js` 和 `039_finding_verification_code.js`，分别保存自动收集队列与生成代码历史；执行继续复用既有验证、执行和证据表。首次使用需由现有启动迁移流程创建这些表。本次实现不自动构建镜像、迁移正式数据库、重启服务或连接真实靶场。

## 判定与统计边界

每条运行证据同时绑定漏洞、计划版本、尝试、载荷编号及内容哈希，并记录载荷是否实际被执行器消费。

- 正常对照正常退出且不含指定特征，完整验证输出出现特征：本地模拟目标达成。
- 两次均完整运行且正常退出，验证输出未出现特征：本次模拟未复现。
- 编译失败、正常对照异常或已含特征、运行超时、输出截断、验证异常退出且缺少特征、证据来源不符：证据不足或未开展适用验证。

系统结果的目标明确标记为“本地模拟输出差异”。它不会提升为真实目标漏洞的 `confirmed`/`not_verified` 结论，也不会增加真实漏洞确认实例数。模型选择的特征可能不合适；运行结果只能支持这一明确的模拟观察目标。

## 验证

- `node --experimental-test-module-mocks --test test/source-code-execution.test.js`：内存数据库、固定模型回复、真实 API 和平台执行链；用测试传输替代容器调度，实际运行固定、已审阅的 Python/C/C++ 样例，覆盖编译失败、载荷变更、权限、重复请求、上限、镜像缺失、宿主机拒绝及本地结论边界。另模拟容器进程检查取消、超时、输出上限和停止确认。没有运行模型生成的任意代码。
- `npm run test:source` 与 `npm test` 包括上述检查及原有源码、HTTP、验证回归。
- `cmake --build build --target RedTeam-FindingPayloadArtifactChecks -j2`；`ctest --test-dir build -R ui-finding-payload-artifacts --output-on-failure`：检查生成、选定产物准备、切换发现及不自动发起执行。

上述固定回复与测试传输不替代现有工具镜像的实际隔离、模型生成质量和真实目标环境验收。实际部署后需在授权测试环境完成额外验收。
