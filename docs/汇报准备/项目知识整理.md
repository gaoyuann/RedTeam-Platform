# RedTeam-Platform 项目知识整理

整理日期：2026-10-13。本文是项目知识资料，不是 PPT 大纲。来源编号见[事实依据与待补材料](事实依据与待补材料.md)。

## 1. 项目在解决什么问题

项目面向授权安全测试和教学实训，将目标配置、资产发现、脆弱性扫描、结果分析、测试预案、受控执行、证据整理及报告输出连接起来。传统工作中需要测试人员分别操作工具、搬运结果、选择下一步并整理报告；本项目把这些环节组织成有状态、有记录、可人工介入的桌面工作流。[D01、D02、C01—C07]

根据现有实现，项目价值可以理解为三个方面：

- 统一组织：用任务关联目标、扫描、预案、执行记录与报告，减少跨页面搬运信息。
- 辅助决策：结合结构化扫描结果、规则、知识资源和大模型生成候选分析与测试方案。
- 过程可追溯：保留审批版本、执行步骤、尝试记录、原始输出、证据与报告来源。

这是对实现的分析判断。当前未发现可直接支撑“效率提升多少”“漏洞发现率提升多少”的受控对比实验，因此不为这些价值添加量化提升结论。

## 3. RedTeam-Platform 的实现架构

当前可从源码核对的主要结构为：

```text
Qt 桌面客户端
    ↓ HTTP API；可用时接收 WebSocket 状态推送
Express 后端：认证、权限、任务与业务接口
    ├─ 任务流水线、分析、预案编辑与审批
    ├─ 执行预检、机械执行/ReAct 执行、取消与状态汇总
    ├─ 工具调度 → Podman / Docker / 支持的主机工具模式
    ├─ 大模型接口与知识资源
    └─ SQLite：扫描、预案、执行、证据、审计与报告等记录
```

上图是逻辑架构说明，不是现场物理网络图。容器中运行第三方安全工具；项目主要承担集成、调度、状态管理和证据组织，不把工具本身的算法认定为本项目原创。[C01、C03、D03]

当前本地 `MainWindow.cpp` 的一级导航为“工作台、测试任务、资产与拓扑、智能分析、预案与知识库、结果与报告、系统管理”。它与旧手册中三项主导航、早期资料中的七个功能模块分类并不相同。后续界面描述应采用最终演示版本，不把历史功能分类当作当前导航。[C01]

当前后端 RBAC 配置使用 `admin`、`user` 两类角色；旧简介中的五角色介绍不能直接作为当前事实。[C08]

## 4. 核心业务闭环

### 4.1 任务与扫描

用户以目标和约束建立测试任务，后端组织扫描及后续工作。扫描结果结构化保存，并成为分析和预案推荐的输入。当前推荐实现限定任务关联的、同目标的已完成或部分完成扫描，还会过滤其他来源的发现，避免混入不同目标的数据。[C02、C04]

“发现某个端口或产品”只能构成测试线索；不自动证明具体漏洞成立。推荐分用于候选排序，不是漏洞概率，也不是利用成功率。[D11、C04]

### 4.2 分析、预案和人工审批

Playbook 表达分步骤测试方案。当前任务计划实现包含草稿、保存、提交、驳回、批准等动作，保留版本与操作记录，并检查审批时的版本是否仍有效。任务计划还保存目标、约束、步骤和候选建议。[C02]

这部分值得作为项目工程工作介绍：让模型建议或既有预案进入可审阅、可修改、可追溯的执行流程。不能把“模型能生成方案”直接等同于“方案已经获批并可运行”。

### 4.3 预检与受控执行

执行器支持机械执行和 ReAct 执行两类模式。执行前检查所需资源和条件，执行中记录工具结果；代码包含人工中止、超时处理、ReAct 决策及动态步骤处理，并调用执行范围检查。[C03]

当前可讨论的技术重点是：模型提出行动后，如何受到工具契约、目标范围、预检、执行状态和人工控制约束。具体动作成功率、长链稳定性和泛化能力仍需要实验。

### 4.4 结果、证据与报告

当前结果服务将扫描候选、分析候选、执行记录和报告来源组织起来，扫描发现默认不自动认定为已确认漏洞。报告相关实现区分执行信息和需要人工复核的风险结论，并对 MITRE 标识进行格式化去重。[C06]

当前执行状态语义已核对：正常结束可以是 `COMPLETED`，即使其中有失败或未执行步骤；人工中止为 `ABORTED`，整体超时等异常仍可能为 `FAILED`。因此汇报中必须分别展示“流程是否结束”“工具执行情况”“证据是否支持漏洞成立”。[C03、D12]

当前代码和测试还体现任务报告直接生成的行为，不应从旧资料推导额外的报告审批步骤。预案审批与报告生成是不同环节。[C06]

## 6. 被测对象与适用边界

演示材料列出三个源代码/教学程序系统和三个 Web 靶场，不等于本次已经完整测试六个对象。[D07]

| 对象 | 特点 | 合理介绍方式 |
| --- | --- | --- |
| vulnerable-webapp | ARM64 C/CGI；资料记录三个 CGI 入口 | 用于服务发现、Web 初筛、源码辅助分析和回显留证；入口数不等于确认漏洞数 |
| vuln-demo.c | ARM64 C 演示服务 | 用于程序与 HTTP 交互验证；具体漏洞数量需要函数级审计和实验 |
| exploit_me | ARM/ARM64 分级教学程序，资料纳入 14 级版本，提供 TCP 交互入口 | 支持特定目标交互与教学复核；14 级不等于平台已自动利用 14 个漏洞，不能按 HTTP 网页处理 |
| DVWA | 综合 Web 靶场，模块和安全级别会影响结果 | 适合作为完整业务闭环案例；需记录版本、级别、Run 和证据 |
| Pikachu | 综合 Web 漏洞教学靶场；资料描述跨架构容器运行 | 适合补充覆盖面；场景数量不等于本次验证数量 |
| SQLi-Labs | 分 lesson 的 SQL 注入教学靶场 | 适合专项分层验证；常见版本的 lesson 总数不等于已完成测试数 |

本项目资料涉及 ARM64 原生程序、x86_64/ARM64 客户端和跨架构容器。操作系统适配、客户端能启动、工具可运行、具体漏洞验证成功是不同层次，不能合并成“全面兼容、全部验证通过”。

## 8. 可供老师进一步讨论的技术问题

以下是分析得到的讨论方向，不是已证实创新性或论文实验结论：

- 大模型建议如何转换成有输入约束、版本记录与审批边界的可执行任务？
- 扫描、执行尝试、结构化发现与人工复核如何共同支持可信报告？
- 固定预案与 ReAct 动态决策在完成率、时间、调用成本和人工介入量上有何差异？
- 相同目标和输入下，PentAGI 工作流与直接模型生成的差异如何客观测量？
- 在国产 ARM64 环境中，客户端、SDK、工具容器和被测二进制各自的适配边界是什么？

现阶段最稳妥的总体判断：项目已形成较丰富的任务、执行和证据管理实现，材料重点正从“功能是否存在”转向“演示是否稳定、结果是否可信、交付是否一致”。这一判断有代码和修复记录支持，但整体成熟度仍需当前版本的完整业务验收。
