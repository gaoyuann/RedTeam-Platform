# F08 逐漏洞验证

## 范围与状态

本轮按项目负责人确认的 F08 Plan 实施，对应 Issue #51。复用 Qt Widgets、F04 原始发现、F06/F07 载荷和现有执行器。原始发现尚未跨工具去重；记录数不是漏洞实例数。

代码与隔离测试不代表真实靶场验收。实际执行、部署版本、认证条件及恢复流程仍需 F01/F02/F07 联调，本功能不自动关闭 #51 或其他前置 Issue。

## 窗口与操作

本窗口按 F08 业务组织，不区分用户类型。扫描页双击一条漏洞直接打开；多条漏洞使用行前复选框，点击“打开勾选的漏洞”。资产、端口、信息和工具错误不进入漏洞验证。勾选随当前任务的结果重绘保留，任务切换时清空；批量打开仅使用当前可见列表中的勾选项，不偷偷加入被过滤隐藏的记录。

窗口左侧显示带复选框的漏洞清单，右侧为三个区域：

1. **漏洞与方案**：查看发现的位置、来源和关键数据；点击“准备验证方案”，系统生成保存草稿。核对目标、步骤、前提、判据和清理说明后确认，再开始验证。打开窗口、准备方案和确认均不会执行工具。
2. **调整方案**：选择模板，调整方案名称、入口、条件、步骤名称、预期证据和判据；按需选择载荷绑定到步骤。工具及结构化输入由生成/模板保留，界面不提供 JSON 参数、变量或版本指纹编辑。新增工具调用需要重新准备方案。保存失败和迟到响应不覆盖新编辑；切换或刷新前保护草稿。
3. **执行结果**：选择某次执行，查看状态、步骤结果和关键观察。原始 JSON、标准输出全文和内部关联字段不直接展示。勾选支持结论的证据并填写依据后保存复核；界面自动关联证据编号，无需手填。缺少结构化观察时明确提示不能据此认定漏洞成立。

“顺序验证勾选项”只运行已准备并确认的漏洞项。清单选择用于查看，复选框用于批量执行，两者独立；每条记录仍有独立版本、尝试和结论。默认最多两次尝试、每次五分钟；未确认实际停止的调用不能重试。单条和队列共用启动/取消处理，迟到响应不能绕过取消；关闭窗口只停止尚未派发的队列，已提交调用继续，明确点击取消后关闭仍保留取消意图。

生成结果仅遗漏目标字段时，服务端使用已核实的发现入口/父任务目标；明确提供的目标仍须通过范围校验。没有合适方案或前提不齐时保留具体原因，不用连通性成功代替漏洞验证。

## 数据与接口

033 迁移新增 `finding_verifications`、`finding_verification_plans`、`finding_verification_attempts`、`finding_verification_reviews`。父任务本来的 `run_id` 与计划不覆盖。发现 ID、扫描归属、计划版本、内容指纹、载荷快照及版本、Run、证据和复核形成关联。

接口前缀 `/api/pipelines/:id/verifications`，要求有效登录且为任务所有者或管理员：

| 方法/相对路径 | 用途 |
| --- | --- |
| GET / | 任务验证项列表 |
| POST / | `{finding_id}` 幂等创建 |
| GET /:verificationId | 当前计划、版本历史、尝试、脱敏证据与载荷 |
| GET /:verificationId/sources | 可用模板及相关性依据 |
| POST /:verificationId/template | `{playbook_id}` 取模板草稿 |
| POST /:verificationId/plans | 保存新版本，须带 `expected_revision` |
| POST /:verificationId/generate | AI 草稿，须带 `expected_revision` |
| POST /:verificationId/preflight | 校验结构、范围、版本；不执行工具 |
| POST /:verificationId/confirm | `revision`、`conditions_confirmed`、`criteria_confirmed` |
| POST /:verificationId/execute | `revision`、`request_id`；重复请求复用尝试 |
| POST /:verificationId/cancel | 请求取消，等待实际停止确认 |
| POST /:verificationId/reviews | `attempt_id`、`conclusion`、`evidence_ids`、`note` |

计划内容包括 `name`、`target`、`source_playbook_id`（可选）、`prerequisites`、`missing_conditions`、`success_criteria`、`cleanup`、`max_attempts`、`duration_ms`、`steps`。步骤包括名称、工具、参数字符串数组、变量、消费方式、载荷及版本（按需）和预期证据。最多 20 步。

400 为输入/引用无效，401 为登录失效，403 为任务权限，404 为归属不符或不存在，409 为版本冲突、未确认条件、活动调用或达到次数上限。AI 生成失败返回 502；最多一次格式纠正，仍不合格返回 422，不保存错误计划。

## 执行和判定

确认后使用只读 Playbook 快照；固定 `mechanical` 执行，不启用自由 ReAct 扩展。执行前和每步检查任务范围，载荷在编译时检查当前可用状态和内容指纹，实际消费冻结版本。输入不保存明文认证值。远端执行位置/认证提供方尚未具备的任务明确阻止启动。

AI 只在执行前生成草稿，或失败后生成新版本。每次最多两次模型调用，每次最多 60 秒，步骤及运行预算由后端校验。自动推断漏洞成立不在本批启用；人工结论须引用当前漏洞、本次尝试的证据。

状态 `queued/running/cancelling` 表示活动调用；`unknown` 表示停止未确认，禁止重试与自动恢复。服务重启后遗留活动尝试进入 `unknown`，不重放。当前没有通过点击按钮直接清除 `unknown` 的功能，须核对实际执行环境后处理；不能仅凭 Run 终态认定停止。

`completed` 仅表示步骤执行结束且步骤成功；漏洞结论另为 `pending/confirmed/not_verified/inconclusive/false_positive`。步骤失败即使旧引擎汇总为 COMPLETED，验证项仍显示执行异常。取消、异常及未验证条目均保留。

任务结果增加逐发现 `verification` 摘要，新报告快照包含该信息并纳入指纹；拓扑按发现及任务关联回填，不以父任务单个 Run 判断。F09 仍负责统一去重与统计口径。F10 应核对尝试的 `stop_confirmed`，不是只看界面标签。

## 验证与回退

新增后端 `finding-verification.test.js`：内存迁移、任务归属、版本、幂等、尝试上限、工具成功与漏洞结论分离、证据错配拒绝、停止未确认、取消，以及真实执行器消费冻结载荷（仅测试创建的本机 HTTP 服务）。自动回归中的模型测试为模拟调用。另使用当前配置的真实模型、必要的脱敏发现上下文和内存数据库核验目录索引、默认文件及管理登录页面的方案准备，三项均成功生成草稿；没有执行目标请求，也没有写回运行库。这只证明生成链路，不证明漏洞成立。

Qt `frontend/tests/finding-verification` 使用本机模拟 API 检查任务/发现上下文、未保存草稿禁止执行、请求版本、状态和迟到响应销毁处理。既有 `ui-context` 回归继续运行。另覆盖单条启动及队列等待启动响应时取消、取消后关闭/销毁窗口；普通关闭不自动取消已提交运行。实际测试结果以交付记录为准。

回退撤回入口和代码接入，保留新表及历史证据，不做删除数据的降级迁移。运行数据库迁移、部署、实际靶场验证另按具体范围授权进行。

## 扫描信息与方案准备结果

Nikto 仅列出 GET、POST、HEAD、OPTIONS 的普通 HTTP 方法枚举属于信息记录，不直接表示漏洞。新扫描按 information/info 保存；旧 web_vuln 记录在读取时重新分类，不改写原始数据。分类筛选、概览、载荷匹配和 F08 入口统一使用此口径。含其他方法或额外风险描述的记录仍保留候选，不自动判定安全。此规则是针对已识别误分类的保守修复，不表示所有 Nikto 输出均已完成语义识别。

“方案未就绪”是准备阶段状态，不是漏洞验证结论。没有步骤、格式校验失败或模型连接失败时显示“方案准备失败，未启动新的验证执行”；没有 Run 或证据就不能称为攻击失败。明确缺少前提时显示“待补条件”；有可执行方案并确认后，才进入启动与执行结果阶段。已有确认方案若重新生成失败，原版本与历史执行保留，不改写为攻击失败。

复查补充：重新准备方案只返回缺失条件或失败时，已有计划版本、确认记录和执行历史保留，页面显示新方案的准备结果。只有尚无计划的验证项改变为“方案未就绪”或“待补条件”。空白、非文字、过长的缺失条件视为无效生成结果；生成返回期间版本或执行状态变化会返回 409，不能用迟到结果覆盖当前状态。

旧记录归为信息后，不允许准备新方案、启动新尝试或作新的漏洞复核；已经关联的历史仍可读取，已启动调用仍可取消。详情接口 `eligible: false` 及 `ineligibility_reason` 标识此情况，客户端禁用新验证操作并保留停止入口。分类调整不删除任何历史数据。

## 方案生成返回格式与入口关联

生成器要求模型直接返回顶层包含 `steps` 的方案实例，同时兼容明确的 `{type, schema: {name, target, steps, ...}}` 包装。只读取这一种无冲突包装，再执行全部既有工具、参数、范围和版本校验；不会在任意嵌套字段中搜索步骤。格式纠正会带上上一条待纠正回答，最多纠正一次。

HTTP 发现入口按扫描事实关联：优先使用属于当前扫描主机且在范围内的发现 URL；已有扫描/任务 HTTP 地址时保留其协议与端口并结合 Nikto 路径；只有裸主机时查同任务、同主机已观察的 HTTP 入口。多个不同端口/协议无法唯一确定、缺少入口或路径越界时列为待补条件，不猜测端口、不自动向目标探测。入口来源通过 `entry_context` 返回，窗口显示具体入口和扫描位置。

默认文件、管理登录页面、目录索引等方案是对扫描线索的复核，成功 HTTP 响应或页面存在不能直接当成高危漏洞利用成立。真正的风险结论仍须结合预设判据、响应证据与人工复核。
