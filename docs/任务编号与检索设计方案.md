# 任务编号与检索设计方案

状态：已按方案实现，验收记录见文末；运行库迁移与服务更新尚未执行。日期：2026-10-23。

目标：任务创建成功即获得固定、唯一、可复制的任务 ID；在列表、详情及后续工作页面中保持一致；用户粘贴这个 ID 即可找到并打开有权查看的任务。

## 1. 当前实现与设计选择

实施前已核实的问题：

- `backend/src/routes/pipelines.js` 在创建时生成 `pipeline_id`，数据库已有唯一约束。修改前生成器截取 UUID 的前 12 个字符，发生冲突时返回创建失败。
- `frontend/src/pages/TaskOverviewPage.cpp` 已在任务概况中显示内部 ID，部分结果页面也显示它，但创建成功反馈、列表和详情顶部未形成统一展示。
- 任务列表目前下载列表后按名称、目标、类型和负责人过滤，过滤内容不含 ID。后端分析索引已支持内部 ID 的文本检索，任务列表接口尚无对应搜索参数。
- 扫描作业、Run、验证尝试、预案和报告均有各自的标识，它们不能代替任务标识。

推荐增加一个面向用户的固定任务编号。界面统一称为“任务ID”，数据库字段命名为 `task_no`；既有 `pipeline_id` 继续承担内部关联和 API 路径定位。用户日常只需使用任务ID。

| 数据 | 职责 | 是否可修改 |
| --- | --- | --- |
| `task_no`，例如 `TASK-20261023-000001` | 用户展示、复制、检索、报告引用 | 创建后不可修改 |
| `pipeline_id` | 内部稳定标识，关联扫描、预案、执行、证据和报告 | 不可修改，旧值保留 |
| `config.task_name` | 用户可读的任务名称 | 允许按原规则修改 |

任务名称允许重复；名称、目标或任务状态变化不影响任务ID。同一目标创建两项任务，必须具有不同任务ID。

## 2. 编号格式与生成规则

推荐格式：`TASK-YYYYMMDD-NNNNNN`，例如 `TASK-20261023-000001`。

- `TASK` 为固定前缀，便于从扫描、Run 和报告编号中识别任务。
- 日期以服务端创建时刻的 `Asia/Shanghai` 日期为准；前端不参与发号。旧任务补号使用原创建日期，UTC 与 SQLite 既有时间格式分别解析，不能直接截取字符串当作本地日期。
- 末段是该日期内的序号，从 1 开始，至少补齐 6 位；超过 999999 时扩展位数，不能截断或循环。
- 编号只在任务成功提交数据库事务后对外返回。界面不预占、不猜测下一个编号。
- 已提交编号永久固定；取消、失败、完成、重启以及删除任务都不能导致已发编号重新分配。发号记录不随任务级联删除。

唯一性由服务端事务和数据库唯一索引共同保证，不能采用查询任务总数加一、前端时间戳或随机短码充当唯一性保证。

建议数据库增加 `pipelines.task_no`、不区分大小写的唯一索引，以及按日期保存已发最大序号的计数表。所有创建入口共用发号函数，在同一个写事务内完成取号、更新计数和插入任务。SQLite 写事务应串行完成，不能把远端源码校验等异步工作放进发号事务。

普通创建、快速创建、拓扑创建共用既有创建接口，使用相同规则。本次不新增扫描重试入口。以后若增加关联重试并实际产生新任务，应共用发号函数并保留原任务关联；任务内部的一次扫描重试或漏洞验证尝试不另建任务ID。

新任务内部 `pipeline_id` 建议改用完整 UUID，两个创建入口统一处理，旧 ID 保留。数据库冲突只允许针对标识冲突有限重试，其他数据库错误正常失败，不得掩盖。

本期唯一性范围为同一平台后端数据库：本地客户端和云笔电连接同一服务器时使用同一发号源。多个独立数据库离线创建后再合并，需要另外设计部署实例前缀或导入映射，不能宣称当前日期序号跨独立平台也唯一。恢复备份时应核对并保留已发序号高水位，防止恢复后重用备份以后的编号。

## 3. 窗口与页面展示

新建窗口继续保持“任务名称 → 测试目标 → 任务类型”，不新增任务ID输入框。

| 位置 | 展示与交互 |
| --- | --- |
| 创建成功 | 显示“任务已创建”及真实任务ID，提供复制和打开任务；完整创建仍保持待启动 |
| 任务列表 | 任务ID使用独立首列，任务名称和目标范围分别展示；根据窗口宽度分配列宽，长文本自动换行并增加行高；右键可复制完整任务ID |
| 任务详情顶部 | 显示任务名称、任务ID及复制操作；切换扫描、分析、预案、验证、评估页签时保持可见 |
| 任务概况 | 基本信息中有独立“任务ID”字段，与顶部一致 |
| 独立打开的任务相关页面、验证窗口 | 显示所属任务ID，避免离开详情外壳后丢失任务身份 |
| 预案、执行、证据、结果 | 任务ID表示所属任务；各对象自身编号明确标为“预案编号”“Run ID”“证据编号”等 |
| 报告列表、预览与新导出文件 | 同时显示报告编号与所属任务ID，便于依据报告返回任务 |

详情顶部复用同一份任务上下文；任务ID仅从后端读取，不由各页面计算或从字符串截取。按实际布局复用公共身份展示组件，保持主界面现有样式。

复制内容为完整编号，不包含标签、空格或省略号。显示“已复制”即可，不增加确认弹窗。任务切换、加载和失败时清理旧编号；接口未返回有效编号时显示明确缺失状态，不能保留上一任务编号或生成一个临时编号冒充。

## 4. 按任务ID检索

主入口使用任务列表现有搜索框，提示改为“搜索任务ID、名称或目标”。沿用现有入口即可完成定位，不依赖当前主界面已移除的全局搜索栏。

完整编号经去除首尾空白、英文字母大小写规范化后，走后端精确查找。搜索结果应展示该任务及其状态，用户点击或回车后打开详情。明确输入完整ID时，定位覆盖全部可见任务，不受当前状态筛选限制；界面说明已按ID定位，清空搜索后恢复此前状态筛选。

普通文本继续搜索名称、目标等字段，增加任务ID匹配。部分编号可匹配前缀；返回多项时展示结果列表，不擅自选中第一项。为兼容已有记录和复制链接，内部 `pipe_...` ID 也可精确定位，但日常页面统一展示用户编号。

检索应由后端执行，覆盖全部有权查看的任务；不能只在当前页或当前下载列表中查找。输入做防抖并丢弃旧响应，避免快速输入或清空搜索后回填旧结果。

建议接口边界：

- `POST /api/pipelines`：创建响应新增 `task_no`，保留所有原字段。
- `GET /api/pipelines`：增加搜索参数，同时保持现有状态参数和响应兼容；普通文本筛选与精确ID定位行为明确区分。
- `GET /api/pipelines/lookup?task_no=...`：规范化后精确定位可见任务，返回真实 `pipeline_id` 和 `task_no`；路由注册在 `/:id` 前。
- `GET /api/pipelines/:pipeline_id` 及任务摘要、分析索引、结果、报告相关响应：补充所属任务编号，原路径保持兼容。

任务ID不是访问凭证。所有查询先按当前账号的访问范围处理，复制他人的编号不能获得读取权限；未知和无权访问的编号在查找入口统一显示“未找到可访问的任务”。本次不扩展任务共享或账号权限。数据库故障、离线和请求超时分别提示检索失败，不能伪装成不存在。

## 5. 旧数据、重复请求与报告兼容

迁移在独立事务内添加字段、补齐旧任务编号并建立唯一约束；按原创建时间和稳定内部顺序发号，同日新任务从补号后的高水位继续。只对缺少编号的任务补号，重复执行检查不得重编已存在编号。无效或缺失历史时间必须列为迁移异常，制定修复规则后再补号，不能静默使用当前日期。

迁移保留全部 `pipeline_id`、外键、任务状态和创建时间，不重新创建任务。上线前在隔离数据库验证；执行运行库迁移按项目部署约定另行授权。旧客户端忽略新增字段仍可工作；新版客户端连接未迁移后端时可以降级显示既有内部 ID 并提示编号功能未就绪，不能把内部 ID 临时格式化为新编号。

编号唯一与请求幂等是两件事。创建按钮提交中禁用；建议创建请求支持 `request_id`，作用域为当前用户。重复请求返回原任务；同一个请求标识携带不同创建内容返回冲突；新请求仍可创建同名任务。网络超时后，重试原请求应能找回原编号。需要把请求与任务的映射存入数据库，不能只靠进程内缓存或编号计数器判断是否重复创建。

新报告冻结快照保存 `task_no` 与 `pipeline_id`。历史报告保持原内容与哈希，不为了补编号改写已保存报告；报告页面可另行展示通过内部关联查到的当前任务编号，并说明它来自当前任务元数据。旧快照导出继续保留原始内部 ID，不将新补号码冒充生成当时已记录的信息。

## 6. 实施顺序与验收

实施按三步完成：先做数据字段、统一发号和检索接口；再贯通创建反馈、任务列表和详情公共标识；最后补齐独立窗口、报告和异常验收。对每一步使用隔离数据验证，最后再验收实际创建与按ID找回。

最小验收清单：

1. 普通、快速、拓扑创建均获得编号；不同任务不重复，同一创建请求重试不重复创建。
2. 多个写连接并发创建、跨日、服务重启、事务失败以及删除后再创建，均不能复用已提交编号。
3. 修改名称、切换状态、补扫、重复漏洞验证，任务ID始终不变。
4. 旧任务补号成功，重复迁移检查保持编号不变；原有任务、扫描、预案、执行和报告关系完整。
5. 复制编号能够检索并打开；大小写和首尾空白可容忍；部分编号出现多项时不自动跳转；当前状态筛选不妨碍完整ID定位。
6. 普通用户无法通过他人的编号读取任务；管理员遵守已有权限；查找不存在、无权访问、断网、服务错误的反馈符合设计。
7. 列表、详情顶部、概况、独立验证窗口和新报告显示同一任务ID；任务切换和迟到响应不会串号。
8. 真实创建一条待启动验收任务，以返回编号从列表和详情找回，并核对持久化记录；仅创建，不发起实际扫描。
9. Qt 构建及相关前后端回归通过，并检查 1024×600、1360×860 和高 DPI 下的可读性、复制及长编号展示。

## 7. 实现与启用

已新增 `backend/src/services/taskIdentity.js` 和迁移 `037_task_identity.js`。普通、快速和拓扑创建共用的接口使用同一发号函数，在立即写事务中分配序号和保存任务；`task_no` 唯一索引及更新保护触发器防止重复和改号。计数与创建请求映射不会随任务删除，序号及请求结果可跨服务重启保留。旧内部 ID 不变，新内部 ID 使用完整 UUID。

创建接口接受顶层可选 `request_id`，相同账号和请求内容重试返回 200 及原任务；首次保存返回 201；同一请求编号更改内容或对应任务已经删除时返回 409。新增 `GET /api/pipelines/lookup?task_no=...`；列表 `search` 支持任务ID、内部 ID 和普通文本，完整ID定位忽略状态筛选，并保持全部可见任务的统计口径。已有详情、分析索引、执行、结果和报告接口补充 `task_no`，旧内部路径不变。任务路由集中核对数据库中的当前账号有效性与角色，避免不同任务入口继续使用失效会话的角色声明。异步配置校验结束后，在立即写事务中再次检查账号启用状态及角色；失效返回 401/AUTH_REQUIRED，不插入任务或请求映射，也不消耗编号。

前端创建成功提供任务ID、复制及打开入口；创建失败保留原请求，仅在提交前已确认后端支持幂等协议时允许显式重试。列表使用独立任务ID列，支持右键复制、输入防抖和回车定位；名称和目标自动换行，时间分成日期、时分秒两行，缩减辅助列空白，尽量在常用窗口宽度内显示全部列。详情公共头部、概况、分析、预案、执行、逐漏洞窗口及结果报告使用同一编号。新报告的编号写入冻结快照；历史报告页面另行说明当前任务元数据来源，不改写旧快照。

列表响应新增 `meta.search_applied=true`，客户端保留后端确认的搜索结果；后端同时匹配任务类型代码和中文显示名，避免两端重复筛选产生漏结果。搜索词在传输前完整编码，`+`、`%`、`&`、`#` 按字面检索。列表响应的 `meta.task_identity_version` 为 1 表示编号与幂等协议可用，未迁移为 0；创建成功响应也返回版本 1。旧后端没有此标志时继续按兼容规则筛选和显示原ID，创建失败提示刷新列表核对，不提供可能造成重复任务的请求重放；后端撤回能力声明时也立即禁用已有待重试请求。

迁移异常历史日期会整体回滚，不使用当前日期补造编号。新版客户端连接旧后端时保留原ID展示及提示；任务编号与幂等创建以更新后的后端为准。申请更新窗口时应先检查运行任务和备份，应用迁移 037、更新后端，再重新打开客户端。本轮未操作运行数据库、重启现有服务或执行真实扫描。

回退时保留新增字段、已发计数和请求映射；旧后端应仅作兼容读取，不能继续用旧创建逻辑生成未编号任务。多个独立数据库合并、备份恢复后的发号高水位核对仍遵循第二节限制。
